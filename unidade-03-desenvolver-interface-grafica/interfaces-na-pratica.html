ComeçoComo usar este guia

Este guia leva você, passo a passo, da pasta vazia até o aplicativo Empresta Aí funcionando no emulador, com o código guardado no GitHub e um histórico organizado. Ele foi escrito para quem está começando: nenhum passo é pulado e cada linha de código vem acompanhada da explicação do que ela faz e de por que foi escrita daquele jeito.

O aplicativo que você vai construir é exatamente o projeto-base que acompanha a apostila. A diferença é que, lá, você recebe o aplicativo pronto; aqui, você o monta peça por peça e entende o papel de cada uma. Ao terminar, você terá praticado o mesmo fluxo de trabalho que a sua squad vai usar no aplicativo do projeto de vocês.

Os sinais usados no guia

Cada passo indica onde ele acontece, porque o trabalho alterna entre o site do GitHub e o seu computador:

  • No GitHub você faz o passo no navegador, no site github.com.
  • No computador você faz o passo no VS Code ou no terminal.

Além disso, aparecem caixas com funções fixas:

O botão Copiar copia o bloco inteiro, mas leia a explicação antes de colar: na avaliação, você vai precisar explicar o código da sua squad.

O que você precisa ter antes de começar

  • O Flutter instalado e funcionando (feito na Aula 2 da apostila), na versão 3.27 ou mais recente.
  • O VS Code com as extensões Flutter e Dart.
  • O Git instalado (no Windows, ele vem no instalador do Git for Windows).
  • Uma conta no GitHub, com o e-mail confirmado.
  • Um emulador Android aberto, ou o navegador Chrome, para ver o aplicativo rodando.

Para conferir se está tudo certo, abra um terminal (no VS Code: menu Terminal → New Terminal) e digite:

terminal: conferir as ferramentas
flutter --version
git --version

Entendendo o código

  1. flutter --version mostra a versão do Flutter instalada. Procure o número logo depois de Flutter, por exemplo Flutter 3.29.0.

Seis palavras que você vai usar o tempo todo

O trabalho com GitHub tem um vocabulário próprio. Os nomes ficam em inglês porque é assim que aparecem no site e nas empresas.

Repositório

A pasta do projeto com todo o histórico de alterações. Existe uma cópia no seu computador (local) e outra no GitHub (remota).

Issue

Uma ficha de tarefa no GitHub: descreve o que precisa ser feito e por quê. Funciona como um cartão num quadro de tarefas.

Branch

Uma linha de trabalho paralela. Você programa numa cópia separada e a versão principal, chamada main, continua funcionando.

Commit

Uma "fotografia" do projeto num momento, com uma frase que descreve o que mudou. O histórico é uma sequência de commits.

Pull Request (PR)

Um pedido para juntar a sua branch à main. Mostra tudo o que mudou e permite que um colega revise antes.

Merge

O ato de juntar a branch à main. Depois do merge, a funcionalidade passa a fazer parte da versão oficial.

ComeçoO ciclo de trabalho

Todas as nove funcionalidades seguem o mesmo ciclo. Na primeira vez, cada passo é explicado em detalhes e com imagens do GitHub; nas seguintes, você só repete a receita. A figura mostra o ciclo completo.

Em forma de receita, o ciclo fica assim:

  1. Escolher a issue no GitHub e marcar você como responsável (Assignee). Assim, a squad sabe quem está cuidando de quê.
  2. Atualizar a main e criar a branch: git switch main, git pull e git switch -c feature/nome-da-funcionalidade.
  3. Programar e testar: criar ou alterar os arquivos, rodar flutter analyze e conferir o resultado no emulador.
  4. Registrar e enviar: git add, git commit -m "..." e git push.
  5. Abrir o Pull Request no GitHub, escrevendo Closes #N na descrição (N é o número da issue), e pedir a revisão de um colega.
  6. Fazer o merge depois da aprovação, apagar a branch no GitHub e voltar para a main no computador.
E se eu estiver fazendo sozinho?

Siga o ciclo do mesmo jeito. Você não consegue aprovar o próprio PR, mas consegue abri-lo, ler a aba Files changed como se fosse outra pessoa e depois fazer o merge. O objetivo é criar o hábito: na squad e no mercado, ninguém coloca código direto na main.

Atenção: os números do seu repositório

O GitHub usa uma única sequência de números para issues e Pull Requests. Como vamos criar as nove issues primeiro (#1 a #9), o primeiro PR recebe o número #10, o segundo #11, e assim por diante. Se você criar as coisas em outra ordem, seus números serão diferentes; use sempre o número que o GitHub mostrar.

Por que essa ordem?

A ordem segue as dependências entre as partes. Primeiro vem a estrutura e o estilo, que todas as telas usam. Depois vêm os dados e as regras, que não dependem de tela nenhuma. Só então vêm as telas, começando pela entrada, que é a primeira que o morador vê. Os testes de tela ficam por último porque precisam do aplicativo completo. Com essa ordem, o aplicativo compila e roda ao final de cada funcionalidade.

Etapa 0 · PreparaçãoCriando o projeto e o repositório

Antes da primeira funcionalidade, é preciso preparar o terreno: apresentar-se ao Git, criar o projeto Flutter, criar o repositório no GitHub e enviar a primeira versão. Esta etapa é feita uma vez por projeto.

1

Apresentar-se ao Git No computador

Cada commit registra o nome e o e-mail de quem o fez. Por isso, na primeira vez que usar o Git num computador, informe esses dados. Use o mesmo e-mail da sua conta do GitHub, para que os commits apareçam ligados ao seu perfil.

terminal: configurar o Git (uma vez por computador)
git config --global user.name "Seu Nome Completo"
git config --global user.email "seu-email@exemplo.com"
git config --global init.defaultBranch main
git config --global pull.rebase false

Entendendo o código

  1. git config altera as configurações do Git. A opção --global faz a configuração valer para todos os projetos deste usuário do computador.
  2. user.name e user.email são o nome e o e-mail que vão aparecer em cada commit. Troque os textos entre aspas pelos seus dados.
  3. init.defaultBranch main faz todo repositório novo começar com a branch chamada main, que é o nome usado pelo GitHub.
  4. pull.rebase false diz ao Git como juntar o seu trabalho com o dos colegas quando os dois mudaram ao mesmo tempo: fazendo um merge, o jeito mais simples. Sem essa configuração, as versões novas do Git recusam o git pull nessa situação e pedem que você escolha.
Atenção: computador do laboratório

Nos computadores compartilhados do Senac, confira com git config --global user.name se não ficou o nome de outra pessoa. Se ficou, rode os comandos acima de novo com os seus dados.

4

Fazer o primeiro commit e enviar No computador

Agora ligamos a pasta do computador ao repositório do GitHub. No terminal do VS Code, dentro da pasta empresta_ai:

terminal: primeiro commit e primeiro envio
git init
git add .
git commit -m "Cria projeto Flutter base"
git branch -M main
git remote add origin https://github.com/seu-usuario/empresta_ai.git
git push -u origin main

Entendendo o código

  1. git init transforma a pasta num repositório Git. Ele cria uma pasta escondida, .git, onde o histórico fica guardado. Nunca apague essa pasta.
  2. git add . prepara todos os arquivos da pasta para o próximo commit. O Git respeita o .gitignore e deixa de fora o que não deve ser guardado.
  3. git commit -m "Cria projeto Flutter base" registra a primeira fotografia do projeto. A mensagem segue o combinado da apostila: verbo no presente seguido do que mudou.
  4. git branch -M main garante que a branch se chame main.
  5. git remote add origin ... registra o endereço do GitHub com o apelido origin. Troque pelo endereço que apareceu no passo anterior.
  6. git push -u origin main envia os commits para o GitHub. O -u memoriza a ligação, e nos próximos envios desta branch basta digitar git push.
A janela de login

No primeiro git push, o Windows abre uma janela pedindo para entrar no GitHub (é o Git Credential Manager). Escolha Sign in with your browser e autorize. Isso só acontece uma vez por computador.

Atualize a página do repositório no navegador: os arquivos do projeto apareceram. Esse é o único commit que vai direto para a main. Daqui em diante, tudo passa por branch e Pull Request.

5

Convidar a squad e o docente No GitHub

No repositório, abra Settings → Collaborators (às vezes aparece como Collaborators and teams), clique em Add people e digite o usuário do GitHub de cada colega e do docente. Cada pessoa recebe um convite por e-mail e precisa aceitá-lo. Só colaboradores podem enviar branches e revisar Pull Requests.

6

Proteger a main (recomendado) No GitHub

Para que ninguém envie código direto para a main por engano, abra Settings → Branches (ou Settings → Rules → Rulesets, nas versões mais novas), crie uma regra para a branch main e marque Require a pull request before merging. A partir daí, o GitHub recusa um git push direto na main e exige um PR. Em repositórios privados de contas gratuitas, essa opção pode não estar disponível; nesse caso, o combinado da squad já basta.

Etapa 0 · PreparaçãoPlanejando o trabalho em issues

Antes de programar, a squad escreve o que vai ser feito. Cada funcionalidade vira uma issue: uma ficha com título, descrição e uma lista do que precisa estar pronto. Escrever primeiro e programar depois evita retrabalho e deixa claro, para todos, quando uma tarefa está concluída.

O que uma boa issue tem

Título com verbo

Diz a ação: "Criar tela de entrada com validação". Evite títulos vagos como "Tela 1" ou "Login".

História do usuário

Uma frase no formato Como [quem], quero [o quê], para [por quê]. Lembra que a tela existe para uma pessoa real.

Lista de tarefas

Os passos técnicos, com caixinhas - [ ]. O GitHub mostra o progresso (por exemplo, "2 de 4") na lista de issues.

Critérios de aceite

Como saber que ficou pronto: o que precisa acontecer na tela. O revisor do PR confere exatamente esses itens.

lib/app.dart · versão da issue #1
import 'package:flutter/material.dart';

/// Raiz do aplicativo. Por enquanto mostra só uma tela provisória;
/// nas próximas issues ela ganha tema, controllers e a tela de entrada.
class EmprestaAiApp extends StatelessWidget {
  const EmprestaAiApp({super.key});

  @override
  Widget build(BuildContext context) {
    return const MaterialApp(
      title: 'Empresta Aí',
      debugShowCheckedModeBanner: false,
      home: Scaffold(
        body: Center(
          child: Text('Empresta Aí em construção'),
        ),
      ),
    );
  }
}

Entendendo o código

  1. As linhas que começam com /// são comentários de documentação. O VS Code mostra esse texto quando você passa o mouse sobre o nome da classe.
  2. class EmprestaAiApp extends StatelessWidget cria um componente chamado EmprestaAiApp. No Flutter, tudo o que aparece na tela é um widget. StatelessWidget é um widget "sem estado": ele só desenha e não guarda nada que mude com o tempo.
  3. const EmprestaAiApp({super.key}); é o construtor, a "receita" para criar o widget. O super.key repassa uma identificação opcional que o Flutter usa internamente. Todo widget começa assim.
  4. @override avisa que estamos reescrevendo um método que já existe na classe-mãe. Widget build(BuildContext context) é o método que o Flutter chama para saber o que desenhar.
  5. MaterialApp é a moldura do aplicativo: guarda o título, o tema e a primeira tela. title é o nome que aparece na lista de aplicativos abertos.
  6. debugShowCheckedModeBanner: false remove a faixa vermelha "DEBUG" do canto da tela.
  7. home é a primeira tela. Scaffold é a estrutura básica de uma tela do Material; Center centraliza o que está dentro; Text mostra um texto. Por enquanto a tela é provisória: ela será trocada pela tela de entrada na funcionalidade 4.

import 'package:flutter/material.dart';

/// Guia de estilo do Empresta Aí transformado em código (Aula 13).
/// Mude a cor-semente e o app inteiro acompanha.
class TemaEmprestaAi {
  static const Color corSemente = Color(0xFF00447C); // azul da agência

  /// Espaçamentos padronizados: use sempre estes valores.
  static const double espacoP = 8;
  static const double espacoM = 16;
  static const double espacoG = 24;

  static ThemeData claro() => _base(Brightness.light);
  static ThemeData escuro() => _base(Brightness.dark);

  static ThemeData _base(Brightness brilho) {
    final cores = ColorScheme.fromSeed(
      seedColor: corSemente,
      brightness: brilho,
    );
    return ThemeData(
      colorScheme: cores,
      // Botões com no mínimo 48 dp de altura: alvo de toque confortável.
      filledButtonTheme: FilledButtonThemeData(
        style: FilledButton.styleFrom(
          minimumSize: const Size.fromHeight(52),
          textStyle: const TextStyle(fontSize: 17, fontWeight: FontWeight.w600),
        ),
      ),
      inputDecorationTheme: const InputDecorationTheme(
        border: OutlineInputBorder(),
      ),
      cardTheme: const CardThemeData(margin: EdgeInsets.zero),
    );
  }
}

Entendendo o código

  1. class TemaEmprestaAi agrupa tudo o que é do tema. Todos os membros são static, o que significa que pertencem à classe, e não a um objeto. Por isso, em qualquer tela, basta escrever TemaEmprestaAi.espacoM, sem precisar criar nada antes.
  2. Color(0xFF00447C) é a cor azul da marca. O 0x indica um número hexadecimal; FF é a opacidade (totalmente opaca) e 00447C é a cor, no mesmo formato usado no CSS e no Figma.
  3. espacoP, espacoM e espacoG são os espaçamentos pequeno (8), médio (16) e grande (24). Usar sempre esses três valores dá um ritmo visual ao aplicativo; números soltos como 13 ou 17 espalhados pelas telas deixam a interface "torta".
  4. static ThemeData claro() => _base(Brightness.light); cria o tema claro. A seta => é um atalho do Dart para uma função que só devolve um valor. O tema escuro é igual, mas com Brightness.dark.

class Item {
  final String id;
  final String nome;
  final String categoria;
  final String dono;
  final String apartamento;
  bool disponivel;

  Item({
    required this.id,
    required this.nome,
    required this.categoria,
    required this.dono,
    required this.apartamento,

Entendendo o código

O controller dos itens No computador

Por que nesta pasta?

controllers/ guarda a camada Controller: as regras ("um item emprestado não pode ser pedido de novo") e o estado ("quais itens eu peguei"). Se essas regras estivessem dentro das telas, seria preciso abrir o aplicativo e tocar em botões para testá-las. Aqui, um teste automático confere tudo em segundos.

lib/controllers/itens_controller.dart
import 'package:flutter/foundation.dart';

import '../dados/itens_exemplo.dart';
import '../models/item.dart';

/// Camada Controller dos itens: busca, pedir e devolver.
/// Quando algo muda, chama notifyListeners() e as telas se redesenham.
class ItensController extends ChangeNotifier {
  final List<Item> _itens = itensDeExemplo();
  final List<Item> _meusPedidos = [];
  String _busca = '';

  List<Item> get itens {
    if (_busca.isEmpty) return List.unmodifiable(_itens);
    final termo = _busca.toLowerCase();
    return _itens
        .where((i) =>
            i.nome.toLowerCase().contains(termo) ||
            i.categoria.toLowerCase().contains(termo))
        .toList();
  }

  List<Item> get meusPedidos => List.unmodifiable(_meusPedidos);

  void buscar(String texto) {
    _busca = texto.trim();
    notifyListeners();
  }

  /// Retorna false se o item já não estava disponível.
  bool pedir(Item item) {
    if (!item.disponivel) return false;
    item.disponivel = false;
    _meusPedidos.add(item);
    notifyListeners();
    return true;
  }

  void devolver(Item item) {
    item.disponivel = true;
    _meusPedidos.remove(item);
    notifyListeners();
  }
}

Entendendo o código

  1. import 'package:flutter/foundation.dart'; traz só a base do Flutter, e não o material.dart: o controller não desenha nada, só precisa do ChangeNotifier.
  2. extends ChangeNotifier dá ao controller a capacidade de avisar quem estiver interessado quando algo muda. É como um grupo de mensagens: as telas "entram no grupo" e recebem um aviso a cada mudança.
  3. _itens, _meusPedidos e _busca começam com _: são privados. Nenhuma tela consegue mexer neles diretamente; para mudar algo, é preciso chamar pedir, devolver ou buscar, que aplicam as regras.
  4. List<Item> get itens é um getter: parece um campo, mas é calculado na hora. Sem busca, devolve todos os itens; com busca, filtra.
  5. .where((i) => ...) filtra a lista, mantendo os itens cuja condição é verdadeira. toLowerCase() transforma tudo em minúsculas, para que "Lazer", "lazer" e "LAZER" encontrem a mesma coisa. contains verifica se o texto contém o termo buscado. O || significa "ou": basta o termo aparecer no nome ou na categoria.
  6. List.unmodifiable(...) entrega à tela uma lista "só para leitura". Se alguma tela tentar adicionar ou remover um item dela, o aplicativo acusa o erro na hora, em vez de deixar o problema escondido.
  7. buscar guarda o termo sem espaços nas pontas (trim()) e chama notifyListeners(), que é o "aviso no grupo": as telas que mostram a lista se redesenham.
  8. pedir devolve bool. A primeira linha é uma verificação de guarda: se o item já não está disponível, a função para ali e devolve false. Só depois vem o caso normal: marcar como emprestado, guardar em "meus pedidos" e avisar as telas.
  9. devolver faz o caminho inverso: marca o item como disponível e o tira da lista de pedidos.

As regras da sessão No computador

Por que nesta pasta?

"O apartamento tem o formato A-302" e "a senha tem 4 números" são regras, e regras moram em controllers/. A tela de entrada só pergunta ao controller se o valor é válido e mostra a resposta. Se, um dia, o aplicativo ganhar uma tela de cadastro, ela usa as mesmas regras, sem copiar código.

lib/controllers/sessao_controller.dart
import 'package:flutter/foundation.dart';

/// Camada Controller da sessão: quem está usando o app e as regras de entrada.
/// As regras de validação ficam aqui, não na tela: a View só mostra a mensagem.
class SessaoController extends ChangeNotifier {
  static final _formatoApartamento = RegExp(r'^[A-Za-z]-?\d{3}$');
  static final _formatoSenha = RegExp(r'^\d{4}$');

  String? _apartamento;

  String? get apartamento => _apartamento;
  bool get logado => _apartamento != null;

  /// Retorna a mensagem de erro, ou null se o valor for válido.
  String? validarApartamento(String? valor) {
    if (valor == null || valor.trim().isEmpty) {
      return 'Informe seu bloco e apartamento.';
    }
    if (!_formatoApartamento.hasMatch(valor.trim())) {
      return 'Use o formato bloco-número, como A-302.';
    }
    return null;
  }

  String? validarSenha(String? valor) {
    if (valor == null || !_formatoSenha.hasMatch(valor)) {
      return 'A senha tem exatamente 4 números.';
    }
    return null;
  }

  /// Retorna true se entrou. A conferência real da senha fica para a UC4.
  bool entrar(String apartamento, String senha) {
    if (validarApartamento(apartamento) != null ||
        validarSenha(senha) != null) {
      return false;
    }
    _apartamento = apartamento.trim().toUpperCase();
    notifyListeners();
    return true;
  }

  void sair() {
    _apartamento = null;
    notifyListeners();
  }
}

Entendendo o código

  1. RegExp(...) cria uma expressão regular: um "molde" que diz qual formato um texto deve ter. A tabela logo abaixo explica o molde do apartamento, peça por peça.
  2. static final: os moldes são criados uma vez só e compartilhados, em vez de serem recriados a cada validação.
  3. String? _apartamento; o ponto de interrogação indica que a variável pode estar vazia (null). Enquanto ninguém entrou, ela é null.
  4. bool get logado => _apartamento != null; responde se há alguém logado: há, se o apartamento não for null.
  5. Os métodos validarApartamento e validarSenha seguem a convenção dos validadores do Flutter: devolvem null quando o valor está certo e um texto com a mensagem de erro quando está errado. É por isso que eles se encaixam diretamente nos campos do formulário, no próximo passo.
  6. As mensagens dizem como corrigir ("Use o formato bloco-número, como A-302"), e não só que está errado. Essa é uma recomendação de usabilidade da Aula 12.
  7. entrar confere as duas regras de novo antes de aceitar (nunca confie só na tela) e guarda o apartamento em maiúsculas com toUpperCase(): quem digitar "a-302" aparece como "A-302".

Entendendo o código

  1. Por que StatefulWidget? Esta tela guarda coisas que mudam enquanto ela está aberta: o texto digitado e se a senha está visível. Widgets que guardam estado são divididos em duas classes: EntradaView (a configuração, que recebe os controllers) e _EntradaViewState (o estado, que guarda o que muda).
  2. required this.sessao, required this.itens: a tela recebe os controllers de quem a cria, em vez de criá-los. A tela usa a sessão para validar e entrar; os itens ela só repassa para a tela inicial, na funcionalidade 5. Dentro do estado, eles são acessados por widget.sessao e widget.itens.
  3. GlobalKey<FormState>() é uma "chave" que dá acesso ao formulário. Com ela, _formKey.currentState!.validate() roda os validadores de todos os campos de uma vez e devolve true se todos passaram. O ! garante ao Dart que o formulário existe.
  4. TextEditingController guarda o texto de um campo. Com ele, _apartamento.text lê o que o morador digitou.
  5. dispose() é chamado quando a tela é fechada. Ali, os TextEditingController são liberados da memória. Todo controller criado num State precisa ser liberado no dispose.
  6. _entrar() valida o formulário; se algo estiver errado, os campos mostram as mensagens e a função para (return). Se estiver tudo certo, chama widget.sessao.entrar(...) e mostra uma SnackBar, a faixa de aviso que aparece na parte de baixo da tela.
  7. Theme.of(context).colorScheme pega as cores do tema criado na funcionalidade 2. A tela não escolhe cor nenhuma: usa cores.primary, que vem da cor-semente.
  8. SingleChildScrollView resolve um problema clássico: em celulares pequenos, o teclado cobre os campos. Com ele, a tela pode rolar.
  9. crossAxisAlignment: CrossAxisAlignment.stretch estica os filhos da Column na horizontal, para que campos e botão ocupem toda a largura.
  10. SizedBox(height: TemaEmprestaAi.espacoM) é um espaço vazio entre os elementos, sempre com os espaçamentos do tema.
  11. No campo do apartamento: textCapitalization.characters liga o teclado em maiúsculas; textInputAction.next troca a tecla Enter por "próximo", que pula para a senha; validator: widget.sessao.validarApartamento liga a regra do controller ao campo. Repare que não há parênteses depois de validarApartamento: estamos entregando a função para o campo usar quando precisar, e não executando a função agora.
  12. No campo da senha: obscureText esconde os caracteres; keyboardType: TextInputType.number abre o teclado numérico; onFieldSubmitted faz o Enter do teclado acionar o _entrar.
  13. O IconButton do olho troca _senhaVisivel dentro de um setState. setState avisa o Flutter de que o estado mudou e a tela precisa ser redesenhada; sem ele, a variável muda, mas a tela não. O tooltip é o texto que o leitor de tela fala para quem não enxerga o ícone (Aula 15).
  14. FilledButton(onPressed: _entrar, ...) usa o estilo do tema: azul, com 52 de altura. Mais uma vez, _entrar sem parênteses: a função é chamada só quando o botão for tocado.
Atenção: com ou sem parênteses?

onPressed: _entrar entrega a função ao botão, que vai chamá-la no toque. onPressed: _entrar() executaria a função na hora de desenhar a tela e entregaria ao botão o resultado dela. É um dos erros mais comuns no Flutter. Quando precisar passar valores, use uma função anônima: onPressed: () => controller.devolver(item).

Entendendo o código

import 'package:flutter/material.dart';

import '../models/item.dart';
import 'icone_categoria.dart';

/// Componente reutilizável: um cartão de item (Aula 9).
/// Semantics junta tudo em uma frase só para o leitor de tela (Aula 15).
class ItemCard extends StatelessWidget {
  const ItemCard({super.key, required this.item, required this.aoTocar});

  final Item item;
  final VoidCallback aoTocar;

  @override
  Widget build(BuildContext context) {
    final cores = Theme.of(context).colorScheme;
    final situacao = item.disponivel ? 'Disponível' : 'Emprestado';

    return Semantics(
      button: true,
      label: '${item.nome}, de ${item.dono}, $situacao',
      excludeSemantics: true,
      child: Card(
        clipBehavior: Clip.antiAlias,
        child: InkWell(
          onTap: aoTocar,
          child: Padding(
            padding: const EdgeInsets.all(12),
            child: Row(
              children: [
                CircleAvatar(
                  radius: 26,
                  backgroundColor: cores.primaryContainer,
                  child: Icon(iconeDaCategoria(item.categoria),
                      color: cores.onPrimaryContainer),
                ),
                const SizedBox(width: 12),
                Expanded(
                  child: Column(
                    crossAxisAlignment: CrossAxisAlignment.start,
                    children: [
                      Text(item.nome,
                          style: Theme.of(context).textTheme.titleMedium),
                      Text('${item.dono} · ${item.apartamento}'),
                    ],
                  ),
                ),
                Chip(
                  label: Text(situacao),
                  backgroundColor: item.disponivel
                      ? cores.secondaryContainer
                      : cores.errorContainer,
                ),
              ],
            ),
          ),
        ),
      ),
    );
  }
}

Entendendo o código

  1. O cartão recebe dois parâmetros: o item a mostrar e aoTocar, do tipo VoidCallback, que é "uma função sem parâmetros e sem retorno". O cartão não sabe o que acontece quando é tocado: quem o usa decide. Isso é o que o torna reutilizável. Na funcionalidade 7, a lista vai mudar o que acontece no toque, e o cartão não vai precisar de nenhuma alteração.
  2. final situacao = item.disponivel ? 'Disponível' : 'Emprestado'; usa o operador ternário: condição ? valor se verdadeiro : valor se falso.
  3. Semantics controla o que o leitor de tela (TalkBack, VoiceOver) fala. label junta tudo numa frase: "Escada de alumínio, de Dona Ilza, Disponível". button: true avisa que é tocável, e excludeSemantics: true evita que o leitor também leia cada texto separadamente (Aula 15).
  4. Card com clipBehavior: Clip.antiAlias recorta o conteúdo nos cantos arredondados, para que a "onda" do InkWell não ultrapasse o cartão.
  5. InkWell(onTap: aoTocar, ...) torna o cartão inteiro tocável. O alvo de toque grande é mais fácil de acertar do que um botão pequeno.
  6. Row põe os filhos lado a lado. Dentro dela, o Expanded faz a coluna de textos ocupar todo o espaço que sobra entre o ícone e o chip. Sem ele, um nome longo como "Escada de alumínio (7 degraus)" ultrapassaria a tela, e o Flutter mostraria uma faixa amarela e preta de overflow.
  7. CrossAxisAlignment.start alinha os textos à esquerda dentro da coluna.
  8. O Chip usa duas cores do tema: secondaryContainer para disponível e errorContainer para emprestado. Repare que a situação também está escrita: a cor nunca é o único sinal, para que pessoas com daltonismo entendam a informação.

Entendendo o código

  1. A tela recebe o item que foi tocado e o controller, que fará o pedido. É StatelessWidget porque não guarda nada próprio: o estado do item fica no controller.
  2. Future<void> _pedir(BuildContext context) async é uma função assíncrona: ela vai precisar esperar o morador responder ao diálogo. async permite usar await dentro dela, e Future indica um resultado que chega "no futuro".
  3. await showDialog<bool>(...) abre a caixa de confirmação e espera o morador escolher. O <bool> diz que a resposta será verdadeiro ou falso.
  4. O texto do diálogo diz exatamente o que vai acontecer, com o nome do dono e do item. Confirmações genéricas ("Tem certeza?") são ignoradas pelas pessoas; confirmações específicas são lidas.
  5. Navigator.pop(context, false) fecha o diálogo e entrega false como resposta; o botão Confirmar entrega true. Esse valor é o que o await recebe em confirmou.
  6. if (confirmou != true || !context.mounted) return; para a função em dois casos. Primeiro, se o morador cancelou ou tocou fora do diálogo, o que fecha a caixa com null; por isso a comparação é com != true, e não com == false. Segundo, se a tela já foi fechada durante a espera (context.mounted falso), não há mais onde mostrar o aviso.
  7. controller.pedir(item) aplica a regra da funcionalidade 3 e devolve se deu certo.
  8. ScaffoldMessenger.of(context).showSnackBar(...) mostra o aviso. A mensagem de erro ("acabou de ser emprestado") parece impossível hoje, mas na UC4, com vários celulares ligados ao mesmo servidor, dois vizinhos poderão pedir o mesmo item ao mesmo tempo. A tela já está preparada.
  9. if (deuCerto) Navigator.of(context).pop(); volta para a lista. O aviso continua visível, porque a SnackBar pertence ao aplicativo, e não a esta tela.
  10. AppBar(title: Text(item.categoria)) é a barra do topo. A seta de voltar aparece sozinha, porque a tela foi empilhada com push.
  11. Container com BoxDecoration desenha a área do ícone grande, com cantos arredondados (BorderRadius.circular(16)) e uma cor do tema. É o espaço onde, no futuro, entraria a foto do item (Aula 8).
  12. textos.titleMedium?.copyWith(color: ...) pega um estilo de texto do tema e muda só a cor. O ?. protege contra um estilo inexistente.
  13. Spacer() ocupa todo o espaço vazio da coluna e empurra o botão para baixo, na zona que o polegar alcança (Aula 4).
  14. onPressed: item.disponivel ? () => _pedir(context) : null: quando onPressed é null, o Flutter desativa o botão e o pinta de cinza automaticamente. O morador vê que não dá para pedir um item emprestado, sem precisar de nenhuma mensagem extra.

Os testes de tela No computador

Por que nesta pasta?

Todo teste fica em test/. O nome widget_test.dart é o que o próprio Flutter usa para testes de tela (widget tests), e é o mesmo nome do arquivo do contador que apagamos na funcionalidade 1. Separar os testes por tipo (controllers_test.dart para regras, widget_test.dart para telas) ajuda a encontrar o teste certo quando algo falha.

test/widget_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';

import 'package:empresta_ai/app.dart';

void main() {
  testWidgets('Entrada recusa formulário vazio', (tester) async {
    await tester.pumpWidget(const EmprestaAiApp());
    await tester.tap(find.text('Entrar'));
    await tester.pump();
    expect(find.text('Informe seu bloco e apartamento.'), findsOneWidget);
  });

  testWidgets('Entrar mostra a lista de itens', (tester) async {
    await tester.pumpWidget(const EmprestaAiApp());
    await tester.enterText(find.byType(TextFormField).at(0), 'A-302');
    await tester.enterText(find.byType(TextFormField).at(1), '1234');
    await tester.tap(find.text('Entrar'));
    await tester.pumpAndSettle();
    expect(find.text('O que você precisa hoje?'), findsOneWidget);
  });

  // Aula 15: o Flutter verifica alvos de toque e contraste automaticamente.
  testWidgets('Tela de entrada segue as diretrizes de acessibilidade',
      (tester) async {
    final handle = tester.ensureSemantics();
    await tester.pumpWidget(const EmprestaAiApp());
    await expectLater(tester, meetsGuideline(androidTapTargetGuideline));
    await expectLater(tester, meetsGuideline(labeledTapTargetGuideline));
    await expectLater(tester, meetsGuideline(textContrastGuideline));
    handle.dispose();
  });
}

Entendendo o código

  1. testWidgets é a versão de test para telas. Ela entrega um tester, o "robô" que abre o aplicativo, toca e digita.
  2. await tester.pumpWidget(const EmprestaAiApp()); abre o aplicativo numa tela virtual. É aqui que se vê a vantagem de ter separado o app.dart do main.dart na funcionalidade 1: o teste cria o aplicativo direto, sem passar pelo main().
  3. find.text('Entrar') procura um widget com esse texto; tester.tap(...) toca nele.
  4. await tester.pump(); redesenha a tela uma vez. No teste, nada se redesenha sozinho: depois de cada ação, é preciso pedir.
  5. expect(find.text('Informe seu bloco e apartamento.'), findsOneWidget); confere se a mensagem de erro apareceu exatamente uma vez.
  6. find.byType(TextFormField).at(0) encontra o primeiro campo de texto da tela; enterText digita nele.
  7. pumpAndSettle() redesenha até todas as animações terminarem. É necessário depois do Entrar, porque a troca de tela tem uma animação de transição.
  8. No terceiro teste, tester.ensureSemantics() liga as informações de acessibilidade, e meetsGuideline confere três diretrizes:
    • androidTapTargetGuideline: todo alvo de toque tem pelo menos 48 × 48 dp;
    • labeledTapTargetGuideline: todo elemento tocável tem um rótulo que o leitor de tela pode falar;
    • textContrastGuideline: o contraste entre texto e fundo é suficiente para leitura.
  9. handle.dispose() desliga as informações de acessibilidade ao final do teste.
