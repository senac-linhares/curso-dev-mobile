Como ler os blocos de código

Os trechos de programação aparecem em blocos com fundo escuro. O texto no topo do bloco indica o arquivo do projeto em que o código deve ser escrito; por exemplo, lib/main.dart significa o arquivo main.dart dentro da pasta lib. As cores ajudam a distinguir as partes do código: comentários aparecem em cinza, textos em verde e palavras reservadas da linguagem em laranja. O botão Copiar copia o conteúdo do bloco.

lib/exemplo.dart
// Comentários aparecem assim.
const nome = 'Empresta Aí';   // texto
final total = 96;              // número
Text('Olá, $nome!');           // um widget

Entendendo o código

  1. As linhas que começam com // são comentários: anotações para quem lê o código. O computador ignora esse texto.
  2. const nome = 'Empresta Aí'; guarda o texto "Empresta Aí" com o nome nome, para ser usado depois.
  3. final total = 96; guarda o número 96 com o nome total.
  4. Text('Olá, $nome!') cria um elemento de tela que exibe um texto. O $nome é substituído pelo valor guardado, e a tela mostra "Olá, Empresta Aí!". Esses conceitos são explicados em detalhe na Aula 9.

Os blocos identificados como terminal contêm comandos que devem ser digitados no terminal: o PowerShell, o Prompt de Comando do Windows ou o terminal integrado do VS Code.

Atenção

Copiar código é permitido e faz parte do aprendizado, mas leia a explicação de cada trecho antes de usá-lo. Na avaliação, você precisará explicar o que o código da sua squad faz e por que ele foi escrito daquela forma.

ReferênciaA UC3 em uma página

A competência desta unidade é desenvolver interface gráfica para dispositivos móveis. A interface gráfica é a parte do aplicativo com que o usuário interage: as telas, os botões, os textos, as imagens, a passagem de uma tela para outra e as respostas que o aplicativo dá a cada toque. É por meio dela que a pessoa usa o sistema; se a interface for confusa, o usuário não consegue aproveitar o que o aplicativo oferece, por melhor que seja o restante do sistema.

Esta unidade trata somente da interface. Guardar informações em um banco de dados, conectar o aplicativo a um servidor ou usar recursos do aparelho, como câmera e localização, são assuntos das UC4 e UC5. Aqui, o objetivo é que o aplicativo tenha telas bem organizadas, responda corretamente ao usuário e possa ser utilizado por qualquer pessoa, inclusive por quem tem baixa visão ou pouca familiaridade com o celular.

A ferramenta adotada pela turma é o Flutter, um kit de desenvolvimento criado pelo Google que permite construir aplicativos para Android, iOS e web a partir de um único código, escrito na linguagem de programação Dart. As características do Flutter e o motivo de sua escolha são apresentados na Aula 1.

1.1 O que é diferente no celular

Um aplicativo móvel não é um site reduzido para caber numa tela menor. O celular tem limitações próprias, como tela pequena e bateria finita, e também possibilidades que o computador não oferece, como câmera, GPS e vibração. Cada uma dessas características interfere diretamente nas decisões de interface. Por isso, muitas das regras que você vai aplicar ao longo desta unidade, como o tamanho mínimo dos botões ou a posição da ação principal, têm origem nas diferenças resumidas na tabela a seguir.

Quando Seu Antônio usa o aplicativo com fonte grande, por exemplo, uma tela com muitos elementos lado a lado simplesmente deixa de caber. Ter essas situações em mente desde o início evita retrabalho nas próximas aulas.

1.2 Plataformas e abordagens de desenvolvimento

Um sistema operacional é o software que controla o aparelho e permite que os aplicativos funcionem nele. No mercado de celulares, dois sistemas operacionais dominam: o Android, mantido pelo Google e presente na maioria dos aparelhos vendidos no Brasil, e o iOS, da Apple, que funciona apenas no iPhone. Como os dois sistemas são diferentes por dentro, um aplicativo precisa ser preparado para cada um deles. Existem três abordagens principais para fazer isso:

AbordagemComo funcionaExemplos de tecnologia
NativoEscreve-se um código separado para cada sistema, na linguagem oficial dele. Oferece o máximo de desempenho, mas o custo de desenvolvimento e manutenção é praticamente dobrado.Kotlin (Android), Swift (iOS)
HíbridoUma página web, feita com HTML, CSS e JavaScript, é executada dentro de um aplicativo. Aproveita o conhecimento de quem já desenvolve para a web.Ionic, Capacitor, Cordova; PWA
Multiplataforma (cross-platform)Um único código gera aplicativos para vários sistemas, com desempenho próximo ao do nativo.Flutter (Dart), React Native (JavaScript), Kotlin Multiplatform

A escolha da abordagem depende do orçamento, do prazo e da equipe disponível. Para uma squad pequena, que precisa entregar o mesmo aplicativo para moradores com Android e com iPhone, manter dois códigos separados seria inviável. A abordagem multiplataforma resolve esse problema, e é por isso que esta unidade utiliza o Flutter.

Conceito-chave

O Flutter é um kit de desenvolvimento de interfaces criado pelo Google. Com um único código escrito na linguagem Dart, ele gera aplicativos para Android, iOS, web e desktop. A diferença em relação à abordagem híbrida é que o Flutter não usa uma página web por dentro: ele desenha cada pixel da tela com seu próprio motor gráfico. Por esse motivo, a interface fica igual em todos os aparelhos, independentemente do sistema operacional.

No mercado

O Flutter é usado em aplicativos de bancos, varejo e mobilidade no Brasil e no mundo, e está entre as tecnologias multiplataforma mais procuradas em vagas para desenvolvedor mobile. Para uma agência pequena, como a que simulamos neste curso, a vantagem é direta: uma única squad mantém um único código e atende aos dois sistemas operacionais.

1.3 Lendo requisitos e wireframes como desenvolvedor

Na UC1, você escreveu requisitos para que o cliente entendesse o que seria construído. Um requisito é a descrição de algo que o sistema deve fazer ou de uma característica que ele deve ter; um wireframe é o desenho simplificado de uma tela, que mostra a disposição dos elementos sem se preocupar com cores ou acabamento. Agora você vai ler esses mesmos documentos com outra pergunta em mente: o que eu preciso construir?

Dona Ilza, como cliente, quer saber se o aplicativo vai resolver o problema do condomínio. Você, como desenvolvedor, precisa saber quantas telas existem, o que há em cada uma e como o usuário passa de uma para outra. Para cada wireframe, procure identificar:

  • Telas: quantas são e qual é o nome de cada uma.
  • Fluxos: a partir de qual tela se chega a qual outra, e por meio de qual botão ou gesto.
  • Elementos: listas, formulários, imagens, botões, abas e demais componentes presentes.
  • Estados: como a tela se apresenta quando está vazia, carregando, com erro ou com sucesso. Os wireframes raramente mostram esses estados, por isso cabe ao desenvolvedor perguntar.
  • Dúvidas: aquilo que o wireframe não responde. Por exemplo: "o que aparece se o morador buscar um item que ninguém cadastrou?"

O item estados merece atenção especial. No Empresta Aí, a lista de itens pode estar vazia logo após a instalação, quando nenhum morador cadastrou nada ainda. Se ninguém pensar nessa situação, o usuário verá uma tela em branco e pode concluir que o aplicativo está com defeito. Registrar essas perguntas antes de programar permite levá-las ao cliente e decidir a resposta com antecedência.

2.3 Criando o emulador

O emulador permite testar o aplicativo sem precisar de um celular físico. Como os usuários do Empresta Aí têm aparelhos diferentes, você vai criar dois emuladores. Siga os passos:

  1. No Android Studio, abra o Device Manager e clique em + (Create Virtual Device).
  2. Escolha um modelo de celular (por exemplo, um Pixel de tela média) e uma imagem de sistema recente.
  3. Crie um segundo emulador, com tela pequena e versão do sistema mais antiga. Ele representa o celular do Sr. Joaquim.

Conceito-chave

Os parâmetros de hardware de um emulador (tamanho e densidade da tela, memória e versão do Android) influenciam a aparência e o comportamento do aplicativo. Testar apenas no emulador mais moderno esconde problemas que o usuário real vai encontrar. Por isso, nesta unidade, trabalhamos sempre com pelo menos dois perfis.

Emulador não abre?

O emulador depende da virtualização, recurso do processador que permite executar um sistema dentro de outro. Ela precisa estar ativada no computador (Intel VT-x ou AMD-V, configurada na BIOS) e, no Windows, também é necessário o recurso Plataforma do Hipervisor do Windows. Se a máquina não oferecer suporte, execute o aplicativo no Chrome (flutter run -d chrome) ou no seu próprio celular conectado por cabo USB (o passo a passo está na Aula 15).

O flutter create gera um projeto com as seguintes pastas e arquivos principais:

Antes de modificar o código, é útil conhecer um termo central do Flutter: widget. Um widget é cada peça da interface, como um texto, um botão ou uma barra de título. A tela inteira é montada encaixando widgets uns dentro dos outros. Esse conceito será aprofundado na Aula 4; por enquanto, basta saber que o código a seguir descreve a tela como uma combinação de widgets.

Substitua todo o conteúdo de lib/main.dart pelo código abaixo, salve o arquivo e observe a tela do emulador mudar:

lib/main.dart
import 'package:flutter/material.dart';

void main() {
  runApp(const MeuApp());
}

class MeuApp extends StatelessWidget {
  const MeuApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      home: Scaffold(
        appBar: AppBar(title: const Text('Olá, Linhares!')),
        body: const Center(
          child: Text(
            'Meu primeiro app Flutter',
            style: TextStyle(fontSize: 24),
          ),
        ),
      ),
    );
  }
}

Entendendo o código

  1. import 'package:flutter/material.dart'; importa a biblioteca de componentes Material, que contém os widgets visuais usados no código, como AppBar e Text.
  2. void main() { runApp(const MeuApp()); } é o ponto de entrada do programa. A função main é a primeira a ser executada, e runApp recebe o widget principal e o exibe na tela.
  3. class MeuApp extends StatelessWidget define um widget chamado MeuApp. Ele é um StatelessWidget (widget sem estado), ou seja, um widget cuja aparência não muda sozinha depois de desenhada.
  4. const MeuApp({super.key}); é o construtor da classe. A palavra const indica que o widget pode ser criado uma única vez e reaproveitado, o que economiza processamento.
  5. O método build, marcado com @override, é chamado pelo Flutter sempre que precisa desenhar o widget. Ele devolve (return) a árvore de widgets que forma a tela.
  6. MaterialApp configura o aplicativo como um todo (tema, navegação). A propriedade home define a primeira tela exibida.
  7. Scaffold fornece a estrutura básica de uma tela: aqui, uma appBar (barra superior com o título "Olá, Linhares!") e um body (corpo da tela).
  8. No corpo, Center centraliza seu filho (child), que é um Text com a frase "Meu primeiro app Flutter" em tamanho 24, definido por TextStyle(fontSize: 24).
Conceito-chave

Hot reload (recarga rápida): ao salvar o arquivo, ou ao pressionar r no terminal, o Flutter injeta a alteração no aplicativo que já está em execução, em menos de um segundo, sem perder o estado da tela (por exemplo, o texto já digitado num campo). Hot restart (reinício rápido), acionado com R, reinicia o aplicativo do zero e descarta o estado. Use o hot reload durante todo o desenvolvimento e recorra ao hot restart quando uma alteração não aparecer, como acontece com mudanças na função main.

Sem computador em casa?

O DartPad (dartpad.dev) executa código Flutter diretamente no navegador, inclusive no celular. Ele não substitui o ambiente completo, mas permite estudar widgets fora do laboratório.

3.1 Ramificações (branches) e tags

O Git é um sistema de controle de versões: ele registra cada alteração feita no código em um commit, que é uma "fotografia" do projeto num determinado momento, acompanhada de uma mensagem que descreve o que mudou. A sequência de commits forma o histórico do projeto. O repositório é o local onde esse histórico fica guardado; ele existe no seu computador e pode ter uma cópia num serviço on-line como o GitHub, chamada de repositório remoto.

Conceito-chave

Uma ramificação (branch) é uma linha paralela de trabalho dentro do mesmo repositório. A branch main guarda a versão que funciona; cada nova tela ou correção é desenvolvida numa branch própria e só retorna à main depois de revisada. Dessa forma, um trabalho em andamento nunca quebra a versão principal. Uma tag (etiqueta) é uma marca fixa num ponto do histórico, como v0.1.0, usada para identificar versões entregues.

O diagrama a seguir mostra esse funcionamento. A linha azul é a main. Duas branches saem dela, uma para a tela de entrada e outra para a lista de itens, recebem seus próprios commits (os círculos) e voltam para a main quando estão prontas. As tags marcam as versões entregues em cada checkpoint.

Para que uma branch volte à main, a squad usa um Pull Request (pedido de integração): uma solicitação, feita no GitHub, para que as alterações de uma branch sejam incorporadas à main. O Pull Request mostra exatamente o que foi alterado e permite que um colega revise o código, comente e aprove antes da integração.

3.2 Combinados da squad

O Git funciona melhor quando toda a equipe segue as mesmas convenções. Nomes padronizados mostram o que é feito em cada branch, e mensagens descritivas tornam o histórico compreensível meses depois. A tabela a seguir apresenta os combinados sugeridos para esta unidade.

ItemCombinado sugerido
Nome das branchesPrefixo que indica o tipo de trabalho, seguido de uma descrição curta: feature/ para funcionalidades novas (feature/tela-entrada, feature/lista-itens) e fix/ para correções (fix/contraste-botao).
Mensagem de commitVerbo no presente seguido do que mudou: Adiciona validação no campo de apartamento. Mensagens genéricas, como "ajustes", não informam o que foi feito e devem ser evitadas.

3.3 Os comandos principais

Os comandos a seguir cobrem três situações: criar o repositório (uma vez por projeto), trabalhar numa tela e marcar uma entrega.

terminal — criar o repositório e o primeiro commit
cd C:\projetos\app_da_squad
git init
git add .
git commit -m "Cria projeto Flutter base"
git branch -M main
git remote add origin https://github.com/SUA-SQUAD/app_da_squad.git
git push -u origin main

Entendendo o código

  1. Dentro da pasta do projeto, git init transforma a pasta num repositório Git, criando a estrutura que guardará o histórico.
  2. git add . seleciona todos os arquivos da pasta (o ponto representa a pasta atual) para fazer parte do próximo commit.
  3. git commit -m "Cria projeto Flutter base" registra o primeiro commit, com a mensagem indicada após -m.
  4. git branch -M main renomeia a branch atual para main, garantindo que o nome siga o padrão adotado.
  5. git remote add origin ... associa o repositório local ao repositório criado no GitHub, que passa a ser chamado de origin. Substitua o endereço pelo da sua squad.
  6. git push -u origin main envia os commits para o GitHub. A opção -u registra essa ligação, de modo que nos próximos envios basta digitar git push.
terminal — trabalhar numa tela
git switch -c feature/tela-entrada     # cria a branch e entra nela
# ... programa, salva, testa ...
git add lib/
git commit -m "Cria leiaute da tela de entrada"
git push -u origin feature/tela-entrada
# no GitHub: abrir Pull Request para a main e pedir revisão

Entendendo o código

  1. git switch -c feature/tela-entrada cria uma nova branch com esse nome (a opção -c significa create, criar) e passa a trabalhar nela. Tudo o que for feito a partir daí fica separado da main. As linhas iniciadas por # são comentários e não são executadas.
  2. git add lib/ seleciona as alterações feitas na pasta lib/ para o próximo commit.
  3. git commit -m "Cria leiaute da tela de entrada" registra o commit na branch atual, seguindo o padrão de mensagem combinado.
  4. git push -u origin feature/tela-entrada envia a branch para o GitHub, onde os colegas podem vê-la.
  5. Por fim, no site do GitHub, você abre um Pull Request da branch para a main e pede a revisão de um colega.
terminal — marcar uma entrega com tag
git switch main
git pull
git tag -a v0.1.0 -m "Checkpoint 1: telas base"
git push origin v0.1.0

Entendendo o código

  1. git switch main volta para a branch principal, pois a tag deve marcar a versão integrada.
  2. git pull baixa do GitHub as alterações mais recentes, incluindo os Pull Requests já aprovados, para que a tag marque a versão atualizada.
  3. git tag -a v0.1.0 -m "Checkpoint 1: telas base" cria uma tag anotada (-a), que guarda o nome de quem a criou, a data e a mensagem informada.
  4. git push origin v0.1.0 envia a tag para o GitHub. Esse passo é necessário porque o git push comum não envia tags automaticamente.
Atenção

O flutter create já gera um arquivo .gitignore configurado corretamente. Esse arquivo lista o que o Git deve ignorar, como a pasta build/, que contém centenas de megabytes gerados automaticamente a cada execução. Como esse conteúdo é recriado a cada build, guardá-lo só tornaria o repositório pesado. Não apague o .gitignore e nunca faça commit da pasta build/.

Aula 4 · DesenvolvimentoLeiaute para aplicativo móvel

4.2 A zona do polegar e o tamanho do toque

A maioria das pessoas segura o celular com uma mão e alcança a tela com o polegar. Nessa posição, a parte inferior e o centro da tela são fáceis de alcançar; os cantos superiores exigem esticar o dedo ou trocar a posição do aparelho. Essa área de alcance confortável é chamada de zona do polegar. Posicionar as ações frequentes dentro dela reduz o esforço do usuário e o risco de o aparelho cair da mão, situação relevante para Marta, que usa o celular com uma mão só.

Além da posição, o tamanho de cada elemento tocável é decisivo. A ponta do dedo cobre uma área muito maior que o cursor do mouse. Botões pequenos e próximos levam a toques errados, especialmente para pessoas com menos coordenação motora fina ou pouca familiaridade com o celular, como Seu Antônio.

Conceito-chave

Todo elemento tocável precisa de uma área de pelo menos 48 × 48 dp, segundo a diretriz do Material Design, do Google, ou 44 × 44 pt, segundo a diretriz da Apple. dp (density-independent pixel, ou pixel independente de densidade) é a unidade usada pelo Flutter, onde é chamada de pixel lógico. Diferentemente do pixel físico, cujo tamanho real varia conforme a densidade da tela, 48 dp têm aproximadamente o mesmo tamanho físico em qualquer celular: cerca de 9 mm, a largura da ponta de um dedo. É por isso que o valor de 48 dp foi adotado como mínimo: ele corresponde ao tamanho do instrumento de toque.

4.4 Leiaute no Flutter: tudo é widget

Na Aula 2, você viu que o Flutter monta a tela com widgets. Esse princípio vale também para o leiaute: no Flutter, não apenas textos e botões são widgets, mas também os espaçamentos, os alinhamentos e as colunas. A tela inteira forma uma árvore de widgets, uma estrutura hierárquica em que cada widget pode conter outros widgets, chamados de filhos; o widget que os contém é o pai.

WidgetO que faz
Column / RowColumn empilha os filhos na vertical; Row os coloca lado a lado, na horizontal.
PaddingCria um espaço interno em volta do filho.
SizedBoxCaixa de tamanho fixo. É muito usada como espaço entre widgets, por exemplo SizedBox(height: 16).
ContainerCaixa que pode ter cor, borda, cantos arredondados, margem e tamanho definidos.
ExpandedDentro de um Row ou Column, faz o filho ocupar todo o espaço que sobrar.

Center, AlignPosicionam o filho dentro do espaço disponível: Center no centro e Align na posição indicada.

Entendendo o código

  1. Card(child: ...) cria a superfície com cantos arredondados e leve sombra. A propriedade child recebe um único filho.
  2. Padding(padding: const EdgeInsets.all(12), ...) adiciona 12 dp de espaço interno em todos os lados (all), para que o conteúdo não encoste na borda do cartão.
  3. Row(children: [...]) coloca os filhos lado a lado. Diferentemente de child, a propriedade children recebe uma lista de widgets, escrita entre colchetes.
  4. CircleAvatar(radius: 26, child: Icon(Icons.handyman)) desenha um círculo com raio de 26 dp contendo o ícone de ferramenta.
  5. SizedBox(width: 12) cria um espaço horizontal de 12 dp entre o ícone e os textos.
  6. Expanded faz a coluna de textos ocupar toda a largura que sobrar no Row depois do ícone, do espaço e do selo. Isso permite que o cartão se adapte a telas de larguras diferentes.
  7. Column com crossAxisAlignment: CrossAxisAlignment.start empilha os dois textos e os alinha à esquerda. O primeiro Text mostra o nome do item em tamanho 16; o segundo, o dono e o apartamento.
  8. Chip(label: Text('Disponível')) exibe o selo de situação, com o texto escrito, conforme a orientação de não depender apenas da cor.
Conceito-chave

A regra fundamental do leiaute no Flutter é: restrições descem, tamanhos sobem, o pai decide a posição. O pai informa ao filho os limites de tamanho que ele pode ocupar (por exemplo, "no máximo esta largura"); o filho escolhe seu tamanho dentro desses limites e o comunica ao pai; o pai, então, posiciona o filho. Quando um Row recebe filhos que, somados, são mais largos que a tela, o Flutter exibe, durante o desenvolvimento, uma faixa amarela e preta indicando overflow (transbordamento). Na maioria dos casos, a solução é envolver o filho que pode encolher com Expanded ou Flexible, para que ele se ajuste ao espaço restante.

4.5 Responsividade

Responsividade é a capacidade de uma interface se adaptar a diferentes tamanhos de tela, orientações e configurações do usuário. O mesmo aplicativo Empresta Aí precisa funcionar no celular pequeno do Sr. Joaquim, num celular comum e até num tablet. Além disso, quando o teclado virtual aparece, o espaço disponível diminui. Três recursos do Flutter resolvem a maior parte dessas situações:

exemplos de responsividade
// 1. Saber o tamanho da tela
final largura = MediaQuery.sizeOf(context).width;

// 2. Mudar o leiaute conforme o espaço disponível
LayoutBuilder(
  builder: (context, restricoes) {
    if (restricoes.maxWidth > 600) {
      return const GradeDeItens(colunas: 2); // tablet
    }
    return const ListaDeItens();               // celular
  },
);

// 3. Rolar quando não couber (telas pequenas, teclado aberto)
SingleChildScrollView(
  child: Column(children: [/* ... */]),
);

Entendendo o código

  1. As linhas iniciadas por // são comentários e não são executadas. MediaQuery.sizeOf(context).width obtém a largura da tela em dp e a guarda na variável largura. A palavra final indica que o valor não será alterado depois de definido.
  2. LayoutBuilder informa ao seu builder as restrições recebidas do pai, aqui chamadas de restricoes. Com isso, a decisão considera o espaço realmente disponível para aquele widget, e não apenas o tamanho total da tela.
  3. if (restricoes.maxWidth > 600) verifica se a largura máxima ultrapassa 600 dp, valor comumente usado para separar celulares de telas maiores. Nesse caso, devolve uma grade com duas colunas; caso contrário, devolve uma lista simples. GradeDeItens e ListaDeItens são nomes ilustrativos de widgets que seriam criados no projeto.
  4. SingleChildScrollView permite rolar o conteúdo quando ele não cabe na tela, situação comum em telas pequenas, com fonte grande ou com o teclado aberto. Sem ele, uma Column com muitos elementos causaria overflow.

O quadro a seguir compara práticas de leiaute frágil, que só funciona em condições ideais, com práticas de leiaute robusto.

Leiaute frágil

  • Larguras fixas em pixels (width: 360), que não se ajustam a telas menores.
  • Botão principal no canto superior direito, fora da zona do polegar.
  • Ações importantes representadas apenas por ícones, sem texto.
  • Testes feitos somente no emulador de tela grande.

Leiaute robusto

  • Larguras relativas (Expanded, double.infinity), que acompanham o espaço disponível.
  • Ação principal na parte inferior, larga e com texto.
  • Ícone acompanhado de rótulo nas ações importantes.
  • Testes feitos no emulador pequeno e com fonte grande.

5.1 Os padrões mais usados e seus widgets

O usuário raramente lê o manual de um aplicativo; ele utiliza o que já aprendeu ao usar outros. Um padrão de design de interação é uma solução recorrente para um problema comum de interação, que os usuários já reconhecem por tê-la visto em muitos aplicativos. Por exemplo, a maioria das pessoas sabe que, ao puxar uma lista para baixo, ela é atualizada. Respeitar esses padrões reduz o esforço de aprendizagem do usuário e também o trabalho da equipe, pois o Flutter já oferece widgets prontos para cada um deles.

Já o feedback de ação responde a uma necessidade básica: sem uma confirmação, o usuário não sabe se o pedido de empréstimo foi enviado e tende a repetir a ação.

5.2 Diretrizes das plataformas

Google e Apple publicam guias oficiais de interface, que descrevem como os componentes devem se parecer e se comportar em cada sistema: o Material Design 3 (m3.material.io), do Google, e as Human Interface Guidelines (diretrizes de interface humana), da Apple. Seguir essas diretrizes faz com que o aplicativo pareça familiar para os usuários de cada plataforma.

O Flutter oferece os dois conjuntos de componentes. Os widgets Material seguem o Material Design e são o padrão adotado nesta unidade; os widgets Cupertino (CupertinoButton, CupertinoNavigationBar, entre outros) reproduzem o visual do iPhone. Como o Flutter desenha a própria interface, os widgets Material funcionam normalmente também no iOS.

No mercado

A maioria dos aplicativos brasileiros feitos em Flutter usa os widgets Material, personalizados com o tema da marca, nas duas plataformas. Componentes específicos são trocados por versões Cupertino, como os seletores de data, apenas quando o cliente solicita. Para o Empresta Aí, os widgets Material atendem às necessidades do projeto e permitem que a squad concentre o tempo nas funcionalidades.

5.3 Referências de mercado e da região

Antes de decidir como será uma interação, é recomendável pesquisar como outros aplicativos resolveram o mesmo problema. Para o Empresta Aí, são boas referências os aplicativos de classificados, os de aluguel de objetos e os próprios aplicativos de condomínio usados em Linhares. Para cada referência, registre três pontos: o que funciona bem, o que causa incômodo e o que é adequado ao público do projeto.

O terceiro ponto é o mais importante. Uma solução que funciona bem para um público jovem e habituado à tecnologia pode não funcionar para Seu Antônio. O quadro a seguir ilustra essa diferença.

6.1 Arquitetura em camadas e o padrão MVC

Arquitetura de software é a forma como o código é dividido em partes que se comunicam. Uma arquitetura em camadas agrupa o código por responsabilidade; assim, quando algo muda, você sabe onde procurar, e a mudança não se espalha. O padrão de camadas mais conhecido em interfaces gráficas é o MVC, sigla de Model-View-Controller (Modelo, Visão e Controlador).

Conceito-chave

MVC divide o aplicativo em três camadas. O Model (modelo) representa os dados e suas regras, como um item ou um pedido. A View (visão) é o que aparece na tela e recebe os toques. O Controller (controlador) recebe as ações do usuário, altera o model e avisa a view de que algo mudou. A regra principal: a view nunca altera os dados diretamente; ela pede ao controller.

Por que a view não pode alterar os dados sozinha? Porque, se cada tela mudasse os dados do seu jeito, as regras ficariam repetidas e poderiam ser aplicadas de forma diferente em cada lugar. Com o controller no meio, a regra "só é possível pedir um item disponível" fica escrita uma única vez. A figura mostra o caminho de um toque no botão Pedir emprestado; siga os números.

6.2 Como o MVC fica no Flutter

O Flutter não impõe nenhuma arquitetura; cada equipe decide como organizar o código, e por isso a squad precisa combinar uma estrutura no início do projeto. Nesta UC, usamos uma versão simples do MVC, em que cada camada corresponde a pastas dentro de lib/, onde fica o código Dart do aplicativo.

estrutura de pastas
lib/
├── main.dart          só chama runApp()
├── app.dart           MaterialApp, tema, primeira tela
├── models/            MODEL: classes de dados (item.dart)
├── controllers/       CONTROLLER: regras e estado, um por assunto
│                      (itens_controller.dart, sessao_controller.dart)
├── views/             VIEW: uma tela por arquivo (itens_view.dart)
├── widgets/           VIEW: pedaços reutilizáveis de tela (item_card.dart)
└── tema/              cores, fontes e espaçamentos (tema.dart)

Entendendo o código

  1. main.dart é o ponto de partida e apenas chama runApp(), que coloca o aplicativo na tela; app.dart monta o MaterialApp, com o tema e a primeira tela.
  2. models/ é a camada Model: classes de dados, como item.dart.
  3. controllers/ guarda as regras e o estado (as informações que mudam durante o uso), com um controller por assunto: itens em itens_controller.dart, entrada do morador (apartamento e senha) em sessao_controller.dart.
  4. views/ (uma tela por arquivo) e widgets/ (pedaços de tela reutilizados, como item_card.dart) formam a camada View.
  5. tema/ reúne cores, fontes e espaçamentos, para que uma mudança visual seja feita em um só lugar.

A camada Model

O model é uma classe Dart comum, que descreve um tipo de dado e não sabe nada sobre telas. No Empresta Aí, o principal é o Item, um objeto disponível para empréstimo, como a furadeira do Seu Antônio.

lib/models/item.dart
class Item {
  final String id;
  final String nome;
  final String dono;
  bool disponivel;

  Item({
    required this.id,
    required this.nome,
    required this.dono,
    this.disponivel = true,
  });
}

Entendendo o código

  1. class Item declara uma classe, um molde para criar objetos; cada item cadastrado será um objeto feito com esse molde.
  2. id, nome e dono são atributos marcados com final: depois de criado o item, não mudam. Já disponivel não é final, porque muda quando o item é emprestado.
  3. Item({ ... }) é o construtor, que cria um novo item. required torna obrigatórios id, nome e dono, e this.disponivel = true faz todo item novo começar disponível.
  4. O arquivo não tem nenhum import do Flutter: o model é independente da tela.

A camada Controller

O controller guarda a lista de itens e as regras para alterá-la. Ele herda de ChangeNotifier, classe do Flutter que sabe avisar quem estiver "ouvindo" que algo mudou. Herdar significa receber automaticamente os recursos de outra classe, entre eles o método notifyListeners().

lib/controllers/itens_controller.dart (resumido)
import 'package:flutter/foundation.dart';
import '../models/item.dart';

class ItensController extends ChangeNotifier {
  final List<Item> _itens = [
    Item(id: '1', nome: 'Furadeira de impacto', dono: 'Seu Antônio'),
    Item(id: '2', nome: 'Escada de alumínio', dono: 'Dona Ilza'),
  ];

  List<Item> get itens => List.unmodifiable(_itens);

  bool pedir(Item item) {
    if (!item.disponivel) return false;
    item.disponivel = false;
    notifyListeners(); // avisa as telas: "algo mudou, redesenhem"
    return true;
  }
}

Entendendo o código

  1. Os import trazem o ChangeNotifier (de foundation.dart) e a classe Item. O controller não importa material.dart, porque não desenha nada.
  2. extends ChangeNotifier faz o controller herdar a capacidade de notificar as telas.
  3. _itens é a lista, iniciada com dois exemplos. O sublinhado no início do nome a torna privada: só pode ser acessada dentro deste arquivo, e nenhuma tela a altera por conta própria.
  4. get itens => List.unmodifiable(_itens) é um getter, uma forma de ler um valor como se fosse um atributo. Ele entrega uma lista que as telas podem ler, mas não modificar.
  5. pedir aplica a regra de negócio: se o item não está disponível (!item.disponivel), devolve false; caso contrário, marca-o como emprestado, chama notifyListeners() para que as telas se redesenhem e devolve true.

A camada View

A view mostra os dados e repassa os toques ao controller. Para que ela se atualize a cada notifyListeners(), usamos o widget ListenableBuilder, que "escuta" o controller e reconstrói seu trecho de tela a cada aviso.

lib/views/itens_view.dart (resumido)
class ItensView extends StatelessWidget {
  const ItensView({super.key, required this.controller});
  final ItensController controller;

  @override
  Widget build(BuildContext context) {
    return ListenableBuilder(
      listenable: controller,
      builder: (context, _) {
        return ListView(
          children: [
            for (final item in controller.itens)
              ListTile(
                title: Text(item.nome),
                subtitle: Text(item.disponivel ? 'Disponível' : 'Emprestado'),
                onTap: () => controller.pedir(item),
              ),
          ],
        );
      },
    );
  }
}

Entendendo o código

  1. ItensView é um StatelessWidget: não guarda dados próprios; tudo vem do controller, que o construtor exige (required this.controller). O super.key repassa uma chave de identificação à classe-mãe, padrão em quase todo widget.
  2. build descreve o que aparece na tela; @override indica que ele substitui um método herdado.
  3. ListenableBuilder liga a tela ao controller: a cada aviso, a função builder é executada de novo. O _ marca um parâmetro que não será usado.
  4. for (final item in controller.itens) cria um ListTile (linha de lista) para cada item. item.disponivel ? 'Disponível' : 'Emprestado' é um operador ternário: condição verdadeira usa o primeiro texto; falsa, o segundo.
  5. onTap: () => controller.pedir(item): no toque, a view não muda o item, apenas pede ao controller.

Os erros mais frequentes de quem começa no MVC têm a mesma origem: misturar responsabilidades.

Atenção: três erros comuns de MVC
  • Model que importa o Flutter. Se item.dart tem import 'package:flutter/material.dart' para guardar um ícone ou uma cor, a camada de dados passou a depender da tela. O correto é guardar só o dado (por exemplo, a categoria do item) e deixar a View decidir qual ícone exibir. No projeto-base, essa decisão fica em widgets/icone_categoria.dart.
  • Regra de negócio dentro da tela. "O apartamento tem o formato A-302" é uma regra do sistema, não da tela. Ela fica no controller, e a View apenas a utiliza: validator: sessao.validarApartamento. Dessa forma, a regra pode ser testada sem abrir nenhuma tela, como mostra o arquivo test/controllers_test.dart.
  • Um controller que faz tudo. Itens e entrada no aplicativo (login) são assuntos diferentes. Por isso, o projeto-base tem dois controllers, ItensController e SessaoController, cada um responsável por um assunto.

6.3 StatelessWidget e StatefulWidget

Todo elemento visual do Flutter é um widget. Os dois tipos básicos diferem no estado: as informações que mudam durante o uso e alteram o que aparece na tela.

StatelessWidget

Widget sem estado próprio: recebe dados e os desenha. A maioria das telas e componentes é assim, como o ItemCard e a PerfilView, mesmo quando os dados vêm de um controller.

StatefulWidget

Widget com estado local, que muda com o uso (a aba selecionada, a senha visível ou não). Para alterá-lo, chama-se setState(() { ... }), que aplica a mudança e redesenha o widget.

Atenção

Onde guardar cada informação depende de quem precisa dela. Estado que só interessa a uma tela (a aba atual, a senha visível ou oculta na tela de entrada) pode ficar no StatefulWidget com setState. Estado que várias telas usam (a lista de itens, os pedidos do morador) deve ficar no controller. Se uma tela guardar uma cópia própria da lista de itens, por exemplo, ela será atualizada e as outras continuarão mostrando a informação antiga. Essa mistura é uma causa frequente do problema "a tela não atualiza".

No mercado

Projetos maiores usam pacotes de gerência de estado (que organizam onde o estado fica e como as telas são avisadas), como Provider, Riverpod ou Bloc, e arquiteturas como o MVVM (Model-View-ViewModel). Todos partem da mesma ideia aplicada aqui: separar tela, regra e dados. Quem compreende o ChangeNotifier tem base para aprender qualquer um deles.

7.1 Marcação e estilo: as linguagens da web

Um aplicativo nativo é escrito na linguagem própria de cada sistema (Kotlin para Android, Swift para iOS). Um aplicativo híbrido é feito com tecnologias da web e "embrulhado" para ser instalado como aplicativo. Uma PWA (Progressive Web App, aplicativo web progressivo) é um site que se comporta como aplicativo (seção 7.3). Híbridos e PWAs usam as três linguagens da web: HTML (HyperText Markup Language), uma linguagem de marcação que define estrutura e conteúdo; CSS (Cascading Style Sheets, folhas de estilo em cascata), que define a aparência; e JavaScript, que define o comportamento. Esses padrões são mantidos pelo W3C (World Wide Web Consortium), organização que também publica as diretrizes de acessibilidade WCAG, usadas na Aula 15.

O exemplo recria em HTML e CSS o cartão de item do Empresta Aí.

item.html — o cartão de item em HTML e CSS
<!DOCTYPE html>

  <meta charset="utf-8">

Entendendo o código

  1. <html lang="pt-BR"> declara o idioma, usado por leitores de tela. No <head>, charset="utf-8" garante os acentos, e a meta tag viewport faz a página usar a largura real do celular.
  2. O bloco <style> contém o CSS. Cada regra começa por um seletor (.card se aplica aos elementos com class="card") e lista propriedades entre chaves.
  3. Em .card, display: flex põe os filhos lado a lado, centralizados na vertical e separados por 12 pixels (gap). Em .icone, border-radius: 50% forma um círculo. .textos { flex: 1; } ocupa o espaço que sobra e empurra o selo para a direita.

7.2 Webstandards: as boas práticas do W3C

Webstandards (padrões web) são as boas práticas que fazem uma página funcionar bem em diferentes navegadores e aparelhos e ser usável por todas as pessoas, inclusive quem usa tecnologias assistivas. As mais importantes para o celular são:

  • HTML semântico: usar a tag que diz o que o elemento é (<button>, <nav>, <h1>), e não <div> para tudo. Leitores de tela dependem disso: um <button> é anunciado como botão; uma <div>, não.
  • Separação de responsabilidades: estrutura no HTML, aparência no CSS, comportamento no JavaScript, o mesmo raciocínio do MVC da Aula 6.
  • Viewport e unidades relativas: a meta tag viewport e medidas proporcionais como %, rem (relativa à fonte base) e vw (percentual da largura da tela) adaptam a página a telas pequenas, como a do Sr. Joaquim.
  • Validação: o código deve passar sem erros no validador do W3C (validator.w3.org).

7.3 Progressive Web Apps (PWA)

Conceito-chave

Uma PWA é um site que se comporta como aplicativo: pode ser instalado na tela inicial do celular, abre em tela cheia e pode funcionar sem internet. Para isso, ela depende de três elementos: HTTPS (conexão segura, com o endereço começando por https://), um arquivo manifest (que informa nome, ícones e cores do aplicativo) e um service worker (um script que roda em segundo plano e guarda arquivos para uso sem conexão).

O manifest usa o formato JSON (JavaScript Object Notation), texto organizado em pares de nome e valor. O celular o lê para saber como exibir a PWA instalada.

manifest.json — o "cartão de identidade" de uma PWA
{
  "name": "Empresta Aí",
  "short_name": "Empresta Aí",
  "start_url": ".",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#00447c",
  "icons": [
    { "src": "icons/Icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "icons/Icon-512.png", "sizes": "512x512", "type": "image/png" }
  ]
}

Entendendo o código

  1. "name" é o nome completo; "short_name", o nome curto exibido abaixo do ícone.
  2. "start_url": "." indica o endereço aberto ao tocar no ícone (o ponto é a própria pasta do site), e "display": "standalone" abre a PWA sem a barra de endereço, com aparência de aplicativo.
  3. "background_color" é o fundo exibido durante o carregamento, e "theme_color", a cor da barra do sistema (o azul do Empresta Aí).
  4. "icons" lista os ícones em 192 e 512 pixels, para o sistema usar o mais adequado.

O Flutter também gera versão web: flutter build web cria a pasta build/web, já com um manifest.json e ícones semelhantes (veja web/manifest.json no seu projeto). A diferença é que o Flutter web desenha a tela em um canvas (área de desenho do navegador), e não em HTML semântico. Por isso, funciona bem para aplicativos, mas é menos indicado que um site comum para conteúdo que precisa ser encontrado por buscadores como o Google, que leem o HTML.

8.1 Formatos de imagem

A compressão com perda descarta detalhes que o olho dificilmente percebe para reduzir o arquivo; a compressão sem perda não descarta nada, mas economiza menos. Uma imagem vetorial é descrita por formas geométricas, e não por pixels, e pode ser ampliada sem perder nitidez.

JPGFotosCompressão com perda; não aceita transparência. Uma qualidade entre 70% e 80% costuma ser imperceptível ao olho.

8.2 Densidade de tela

No Flutter, os tamanhos são medidos em dp (density-independent pixel, pixel independente de densidade), unidade que mantém o tamanho visual parecido em telas diferentes. Porém, cada tela coloca uma quantidade diferente de pixels físicos em cada dp, e uma imagem com poucos pixels fica borrada em uma tela que tem muitos.

Conceito-chave

Densidade é a quantidade de pixels físicos que cabem em cada dp. Um celular simples pode ter 2 pixels por dp; um modelo topo de linha, 3 ou mais. Para que uma imagem de 100 × 100 dp fique nítida em todos eles, você fornece versões com 100, 200 e 300 pixels de lado, e o Flutter escolhe automaticamente a versão certa para cada aparelho.

Para que o Flutter encontre as versões, a imagem base fica na pasta principal e as maiores, em subpastas com o nome do fator de densidade.

organização das imagens no projeto
assets/
└── imagens/
    ├── logo.png          100 × 100 px  (1x)
    ├── 2.0x/
    │   └── logo.png      200 × 200 px
    └── 3.0x/
        └── logo.png      300 × 300 px

Entendendo o código

  1. assets/imagens/ fica na raiz do projeto, fora de lib/. Asset (recurso) é qualquer arquivo que acompanha o aplicativo, como imagens e fontes.
  2. logo.png de 100 × 100 px é a versão 1x; as pastas 2.0x/ e 3.0x/ têm arquivos com o mesmo nome e o dobro e o triplo de pixels. O nome idêntico permite ao Flutter reconhecê-los como variantes da mesma imagem.

Além de organizar as pastas, é preciso informar ao Flutter que essas imagens fazem parte do aplicativo. Isso é feito no pubspec.yaml, o arquivo de configuração do projeto, escrito no formato YAML (um formato de texto em que a hierarquia é indicada pela indentação).

pubspec.yaml — declarar as imagens
flutter:
  uses-material-design: true
  assets:
    - assets/imagens/

Entendendo o código

  1. flutter: abre a seção de configurações do Flutter; uses-material-design: true inclui a fonte de ícones Material, usada por Icon(Icons.handyman).
  2. assets: inicia a lista de recursos, em que cada item começa com hífen.
  3. - assets/imagens/ declara a pasta inteira: a barra final inclui todos os arquivos dela, e o Flutter reconhece sozinho as variantes em 2.0x/ e 3.0x/.
Atenção

O pubspec.yaml usa indentação com espaços (nunca Tab), e ela tem significado: assets: fica dois espaços para dentro de flutter: porque pertence a essa seção; um espaço a mais ou a menos causa erro. Depois de alterar o arquivo, pare o aplicativo e execute flutter run de novo, pois o hot reload (recarga rápida) não carrega imagens novas.

Com as imagens declaradas, elas podem ser usadas no código. O exemplo abaixo mostra três situações comuns: uma imagem do próprio aplicativo, uma foto grande que precisa economizar memória e uma imagem baixada da internet.

usando imagens no código
// Imagem do próprio app (o Flutter escolhe 1x, 2x ou 3x)
Image.asset(
  'assets/imagens/logo.png',
  width: 100,
  semanticLabel: 'Logotipo do Empresta Aí',
);

// Foto grande: decodifica já no tamanho exibido, economizando memória
Image.asset(
  'assets/imagens/escada.webp',
  height: 160,
  fit: BoxFit.cover,
  cacheHeight: 480, // 160 dp × densidade 3
);

// Imagem da internet, com o que mostrar enquanto carrega e se falhar
Image.network(
  'https://exemplo.com/furadeira.webp',
  loadingBuilder: (context, child, progresso) =>
      progresso == null ? child : const CircularProgressIndicator(),
  errorBuilder: (context, erro, pilha) => const Icon(Icons.broken_image),
);

Entendendo o código

  1. No primeiro exemplo, Image.asset exibe uma imagem declarada no pubspec.yaml. Basta indicar o caminho da versão 1x; o Flutter escolhe a variante conforme o aparelho. semanticLabel é a descrição lida pelo leitor de tela, sem a qual uma pessoa cega não saberia o que a imagem representa.
  2. No segundo, fit: BoxFit.cover faz a imagem preencher os 160 dp de altura, cortando as sobras. cacheHeight: 480 carrega a imagem na memória já com 480 pixels de altura (160 dp × densidade 3), e não no tamanho original, o que poupa memória em aparelhos como o do Sr. Joaquim.
  3. No terceiro, Image.network baixa a imagem da internet. Em loadingBuilder, enquanto progresso tiver valor a imagem ainda está chegando e aparece o indicador circular de carregamento; quando for null, exibe-se a imagem (child). errorBuilder mostra um ícone de imagem quebrada se o carregamento falhar, por exemplo sem internet.

8.3 Como otimizar uma imagem

Otimizar uma imagem é reduzir o arquivo o máximo possível sem prejudicar a qualidade percebida. Siga estes passos, nesta ordem:

  1. Redimensione para o maior tamanho em que a imagem aparece, em pixels, já multiplicado pela densidade 3x. Uma foto de 4000 px para um espaço de 360 dp é desperdício: 360 × 3 = 1080 px bastam.
  2. Converta para o formato adequado: fotos em WebP ou JPG; ícones em SVG ou PNG.
  3. Comprima com uma ferramenta como o Squoosh (squoosh.app, no navegador) ou o TinyPNG.
  4. Meça o antes e o depois e anote o ganho, que é evidência para o relatório.
  5. Prefira ícones a imagens quando possível: o Flutter já traz milhares de ícones Material (Icon(Icons.handyman)), que não pesam nada.

Propriedade intelectual é o conjunto de direitos de quem criou uma obra, como fotos, ícones, fontes e marcas. Uma licença é a autorização do autor que define como a obra pode ser usada. Por isso, imagem encontrada no Google não é imagem livre: ela tem autor, e usá-la sem autorização pode gerar problemas legais para a squad e o cliente. 9.1 O essencial de Dart

Antes de ler o código, conheça os conceitos que ele usa:

  • Variável é um nome que guarda um valor na memória. Todo valor tem um tipo, que diz que espécie de dado ele é: String (texto, entre aspas), int (inteiro), double (número com casas decimais), bool (true ou false), List (lista em ordem) e Map (pares de chave e valor). Com var, o Dart deduz o tipo pelo valor; de todo modo, o tipo fica fixo, o que ajuda a achar erros antes de rodar.
  • final: a variável recebe valor uma única vez, mesmo que ele só seja conhecido durante a execução. const: o valor precisa ser conhecido antes de o programa rodar. Ambos evitam alterações acidentais.
  • Interpolação é inserir um valor dentro de um texto: $nome para uma variável, ${...} para uma expressão.
  • Null safety (segurança contra nulos): null é a ausência de valor, e usá-lo como valor real é causa comum de falhas. Por isso, nenhuma variável pode ser nula, a menos que o tipo tenha ? (como String?); então a linguagem obriga a tratar a ausência com ?? (valor padrão) ou ?. (acesso seguro).
  • Função é um bloco de código com nome que executa uma tarefa e pode devolver um resultado; recebe valores chamados parâmetros. Parâmetros nomeados, entre chaves, são escritos com o nome na chamada, o que deixa claro o significado de cada valor. Funções de uma só instrução podem usar => (arrow function, função seta).
  • Classe é o molde de um tipo de objeto, como o Item da Aula 6. Todo widget é uma classe.
  • if e for podem ser usados dentro de listas, o que permite incluir um elemento só em certas condições ou criar um elemento para cada valor de uma coleção.

Em um programa real, comandos como print(...) ficam dentro de uma função (por exemplo, main()); no bloco abaixo, eles aparecem soltos apenas para facilitar a consulta.

// Variáveis
var cidade = 'Linhares';      // tipo deduzido (String)
String bloco = 'B';           // tipo explícito

  return 'Bom $periodo, $nome!';

  'Título',

  for (final c in categorias) c,

Entendendo o código

  1. Variáveis. var cidade tem o tipo String deduzido; String bloco tem o tipo escrito. final hoje guarda a data e hora do momento da execução e não aceita outro valor; const moradores = 96 é fixo desde antes de o programa rodar. O texto após // é um comentário, ignorado pelo computador.
  2. Tipos. double usa ponto nas casas decimais (9.5). List<String> é uma lista que só aceita textos, entre colchetes; Map<String, int> associa chaves de texto a números, entre chaves (a chave 'escada' vale 1).
  3. Interpolação. print exibe o texto no console: Moradores: 96, cidade: LINHARES, pois toUpperCase() converte para maiúsculas.
  4. Null safety. String? apelido; pode ser nula e, sem valor atribuído, vale null. Por isso, apelido ?? 'sem apelido' exibe "sem apelido", e apelido?.length devolve null em vez de causar erro.
  5. Funções. Em saudacao, nome é obrigatório e periodo vale 'dia' se não for informado; return devolve o resultado. A chamada saudacao(nome: 'Dona Ilza') produz Bom dia, Dona Ilza!. Em dobro, a seta substitui as chaves e o return.
  6. Classe. Morador tem dois atributos final, e seu construtor const exige ambos, permitindo criar, por exemplo, const Morador(nome: 'Marta', apartamento: 'A-101').
  7. if e for em listas. "Aviso" só entra porque mostrarAviso é true, e o for acrescenta cada categoria. A lista final é ['Título', 'Aviso', 'Ferramentas', 'Cozinha', 'Lazer']; em uma tela, seriam widgets no lugar dos textos.
Conceito-chave

Use const sempre que um widget não depender de nada que mude, como const Text('Entrar') ou const SizedBox(height: 16). O Flutter reaproveita widgets constantes em vez de recriá-los a cada redesenho, e o aplicativo fica mais leve. O VS Code sublinha onde é possível acrescentar const.

Escolher o componente certo importa porque cada um já traz o comportamento e a acessibilidade esperados: um FilledButton, por exemplo, é anunciado como botão pelo leitor de tela.

9.3 Montando uma tela a partir do wireframe

Trabalhe sempre na ordem esqueleto → blocos → conteúdo → acabamento: primeiro o Scaffold e a estrutura principal; depois os blocos, se quiser com cores provisórias; em seguida os textos e imagens reais; só no final os espaçamentos finos e o tema. Essa ordem evita gastar tempo com acabamento antes de a estrutura estar correta, pois uma mudança na estrutura pode desfazê-lo. O código abaixo é a tela inicial do Empresta Aí nas etapas de esqueleto e blocos, ainda com dados provisórios.

lib/views/inicio_view.dart — versão inicial
import 'package:flutter/material.dart';

class InicioView extends StatelessWidget {
  const InicioView({super.key});

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Empresta Aí')),
      body: ListView.builder(
        padding: const EdgeInsets.all(16),
        itemCount: 10,
        itemBuilder: (context, i) {
          return Card(
            child: ListTile(
              leading: const Icon(Icons.handyman),
              title: Text('Item ${i + 1}'),
              subtitle: const Text('Dono · Apartamento'),
              trailing: const Icon(Icons.chevron_right),
              onTap: () {},
            ),
          );
        },
      ),
    );
  }
}

Entendendo o código

  1. O import de material.dart traz os componentes visuais; por ser uma view, este arquivo precisa dele.
  2. build devolve um Scaffold cuja appBar exibe o título, marcado como const porque nunca muda.
  3. Em body, o ListView.builder cria a lista, com 16 dp de margem interna (EdgeInsets.all(16)) e, por enquanto, dez itens de exemplo (itemCount: 10).
  4. itemBuilder é chamada para construir cada item. O i é a posição, começando em zero; por isso o título usa ${i + 1} e exibe "Item 1", "Item 2" e assim por diante.
  5. Cada item é um Card com um ListTile: leading é o ícone à esquerda, title e subtitle são os textos e trailing é a seta que indica que o item pode ser aberto. onTap: () {} é uma função vazia: o item já responde ao toque, mas a navegação só virá nas próximas aulas.

9.4 Extraindo componentes

Extrair um componente é transformar um trecho de tela em um widget próprio, com nome, reutilizável. Faça isso quando um trecho aparece em mais de uma tela ou quando o build passa de cerca de 60 linhas. No VS Code, clique no widget, pressione Ctrl + . e escolha Extract Widget; depois, mova a nova classe para um arquivo em widgets/. O exemplo abaixo é o botão de ação principal do Empresta Aí: largo e alto, para facilitar o toque da Marta com uma mão, e com texto maior, para ajudar o Seu Antônio.

lib/widgets/botao_principal.dart
import 'package:flutter/material.dart';

/// Botão largo, com ícone e texto, para a ação principal da tela.
class BotaoPrincipal extends StatelessWidget {
  const BotaoPrincipal({
    super.key,
    required this.texto,
    required this.icone,
    required this.aoTocar,
  });

  final String texto;
  final IconData icone;
  final VoidCallback? aoTocar; // null = botão desabilitado

  @override
  Widget build(BuildContext context) {
    return SizedBox(
      width: double.infinity,
      height: 52,
      child: FilledButton.icon(
        onPressed: aoTocar,
        icon: Icon(icone),
        label: Text(texto, style: const TextStyle(fontSize: 17)),
      ),
    );
  }
}

// Uso:
// BotaoPrincipal(texto: 'Pedir emprestado', icone: Icons.handshake, aoTocar: _pedir)

Entendendo o código

  1. A linha com /// é um comentário de documentação, que o VS Code exibe ao passar o mouse sobre BotaoPrincipal.
  2. O construtor exige texto, icone e aoTocar. São esses parâmetros que tornam o componente reutilizável: cada tela informa seu texto, ícone e ação. IconData é o tipo dos ícones, como Icons.handshake.
  3. VoidCallback? é o tipo de uma função sem parâmetros e sem retorno, aqui podendo ser nula; quando aoTocar é null, o Flutter exibe o botão desabilitado.
  4. O SizedBox define o tamanho: width: double.infinity ocupa toda a largura disponível e height: 52 dá uma altura confortável para o toque.
  5. FilledButton.icon é o botão principal com ícone; onPressed: aoTocar liga o toque à função recebida. As linhas comentadas no final mostram um exemplo de uso.
No mercado

Equipes profissionais mantêm uma biblioteca de componentes: widgets próprios (botão, cartão, campo) usados em todas as telas. Se o cliente pedir para mudar o arredondamento dos botões, altera-se um arquivo e o aplicativo inteiro acompanha. É essa biblioteca que vocês documentarão no Manual de Interface da Aula 18.

11.1 Respondendo ao toque

Quando o usuário encosta o dedo na tela, o sistema gera um evento de toque. Para que algo aconteça, o widget precisa ter um callback (função de retorno) associado ao evento: uma função que o Flutter executa no momento do toque. Os botões do Material, como FilledButton, recebem essa função no parâmetro onPressed.

Para tornar tocáveis outros elementos, como um cartão ou uma imagem, o Flutter oferece dois widgets que envolvem qualquer outro. O InkWell exibe o efeito de ondulação (ripple) do Material Design, que confirma visualmente que o toque foi percebido. O GestureDetector reconhece mais gestos, como toque duplo e arrastar, mas não exibe efeito visual. Use InkWell para cartões e itens de lista, e GestureDetector apenas quando precisar de gestos que o InkWell não reconhece.

eventos de toque
// Botão: o jeito mais simples
FilledButton(
  onPressed: () => print('tocou'),
  child: const Text('Pedir'),
);

// Qualquer widget tocável, com efeito visual
Card(
  clipBehavior: Clip.antiAlias, // a "onda" respeita os cantos arredondados
  child: InkWell(
    onTap: () => abrirDetalhe(),
    onLongPress: () => mostrarOpcoes(),
    child: const ListTile(title: Text('Escada de alumínio')),
  ),
);

// Gestos mais avançados (arrastar, toque duplo), sem efeito visual
GestureDetector(
  onDoubleTap: () => favoritar(),
  child: const Icon(Icons.favorite_border),
);

Entendendo o código

  1. Em onPressed: () => print('tocou'), a função anônima só é executada quando o botão é tocado.
  2. O InkWell fica dentro do Card e envolve o ListTile, tornando toda a área do cartão tocável. onTap trata o toque simples e onLongPress, o toque longo.
  3. clipBehavior: Clip.antiAlias recorta o conteúdo nos cantos arredondados do cartão; sem isso, a ondulação ultrapassaria as bordas.
  4. O GestureDetector reconhece o toque duplo (onDoubleTap), mas não mostra ondulação. As funções abrirDetalhe(), mostrarOpcoes() e favoritar() representam ações escritas por você.
Atenção

Toque longo, toque duplo e deslizar são gestos ocultos: nada na tela indica que eles existem. Por isso, um gesto oculto nunca deve ser o único caminho para uma ação. Seu Antônio dificilmente descobrirá sozinho que precisa manter o dedo pressionado sobre um item. Use esses gestos apenas como atalhos e ofereça sempre um botão visível para a mesma ação.

11.2 Alternância entre telas com o Navigator

Cada tela completa de um aplicativo Flutter, como a lista de itens ou o detalhe de um item, é chamada de rota (route). O widget que controla quais rotas estão abertas e qual aparece para o usuário é o Navigator.

Conceito-chave

O Navigator organiza as telas como uma pilha, semelhante a uma pilha de pratos. O método push (empurrar) coloca uma tela nova no topo, e é ela que o usuário passa a ver. O método pop (retirar) remove a tela do topo e revela a anterior. O botão "voltar" do Android e a seta da AppBar executam um pop automaticamente.

O Empresta Aí precisa de quatro operações: abrir o detalhe do item tocado, voltar à lista, trocar a tela de entrada pela inicial depois do login e abrir uma tela que devolve uma resposta.

abrir uma tela passando dados, e voltar
// Na lista: abrir o detalhe do item tocado
Navigator.of(context).push(
  MaterialPageRoute(
    builder: (context) => ItemDetalheView(item: item),
  ),
);

// No detalhe: voltar para a lista
Navigator.of(context).pop();

// Trocar a tela atual sem permitir voltar (ex.: depois do login)
Navigator.of(context).pushReplacement(
  MaterialPageRoute(builder: (context) => const InicioView()),
);

// Esperar uma resposta da tela que foi aberta
final confirmou = await Navigator.of(context).push<bool>(
  MaterialPageRoute(builder: (context) => const ConfirmarView()),
);
// e, na ConfirmarView: Navigator.of(context).pop(true);

Entendendo o código

  1. Navigator.of(context) localiza o Navigator a partir do context, que indica a posição do widget na árvore de widgets.
  2. MaterialPageRoute cria a rota com a animação padrão da plataforma; seu builder constrói a nova tela. Em ItemDetalheView(item: item), o item tocado é passado pelo construtor.
  3. pop() remove a tela atual e o usuário volta à lista.
  4. pushReplacement substitui a tela atual em vez de empilhar. Depois do login, a tela de entrada sai da pilha e o voltar não retorna a ela.
  5. push<bool> indica que a tela aberta devolverá um valor verdadeiro ou falso. Quando a ConfirmarView executa pop(true), o true chega a confirmou. O await faz o código esperar a tela ser fechada; esse mecanismo é explicado na Aula 12.

11.3 Navegação inferior com abas

As seções principais do aplicativo (Itens, Meus pedidos e Perfil) são visitadas o tempo todo, em qualquer ordem. Para elas, não se empilham rotas: usa-se a navegação inferior por abas com NavigationBar, apresentada na Aula 5. Ao tocar em uma aba, apenas o corpo da tela é trocado.

A aba selecionada é um dado que pertence só a essa tela, ou seja, um estado local. Por isso, usamos um StatefulWidget e atualizamos o valor com setState, que avisa o Flutter de que a tela precisa ser redesenhada. Dados compartilhados entre telas continuam nos controllers, conforme o padrão MVC.

lib/views/inicio_view.dart (versão simplificada; no projeto-base as abas recebem os controllers)
class InicioView extends StatefulWidget {
  const InicioView({super.key});

  @override
  State<InicioView> createState() => _InicioViewState();
}

class _InicioViewState extends State<InicioView> {
  int _abaAtual = 0;

  final _abas = const [ItensView(), PedidosView(), PerfilView()];

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: SafeArea(child: _abas[_abaAtual]),
      bottomNavigationBar: NavigationBar(
        selectedIndex: _abaAtual,
        onDestinationSelected: (i) => setState(() => _abaAtual = i),
        destinations: const [
          NavigationDestination(icon: Icon(Icons.search), label: 'Itens'),
          NavigationDestination(icon: Icon(Icons.inventory_2_outlined), label: 'Meus pedidos'),
          NavigationDestination(icon: Icon(Icons.person_outline), label: 'Perfil'),
        ],
      ),
    );
  }
}

Entendendo o código

  1. _abaAtual guarda o índice da aba selecionada; 0 é a primeira (Itens). _abas lista as três telas na mesma ordem dos botões.
  2. No body, _abas[_abaAtual] escolhe a tela exibida. O SafeArea evita que o conteúdo fique sob a barra de status.
  3. selectedIndex destaca a aba atual, o que mostra ao usuário onde ele está.
  4. Ao tocar em uma aba, onDestinationSelected recebe o índice em i; dentro de setState, _abaAtual é atualizado e o build é executado de novo.
  5. Cada NavigationDestination tem ícone e rótulo de texto, pois ícones sozinhos podem ser interpretados de formas diferentes.
No mercado

Aplicativos com muitas telas costumam usar rotas nomeadas, em que cada tela tem um endereço em texto, e o pacote go_router, que permite endereços como /itens/12 e deep links (links que abrem o aplicativo direto em uma tela). Para o tamanho dos projetos desta UC, o Navigator.push atende bem e é mais simples.

11.4 Limitações e possibilidades de navegação

Além de programar a navegação, é preciso decidir como ela deve se comportar. Use os critérios abaixo para avaliar o fluxo da sua squad.

  • Profundidade: é o número de toques até a informação desejada. Cada tela intermediária é uma chance a mais de o usuário se confundir; se a tarefa principal exige mais de três toques, repense o fluxo.
  • Voltar previsível: o voltar deve levar aonde o usuário espera. Depois do login, ele não deve retornar à tela de senha, o que daria a impressão de ter saído da conta; por isso se usa pushReplacement.
  • Sair sem perder dados: se o usuário preencheu parte de um formulário e toca em voltar, pergunte antes de descartar. O widget PopScope permite interceptar o voltar.
  • Orientação: o título na AppBar e a aba destacada devem indicar sempre em que parte do aplicativo o usuário está.

12.1 O teclado certo para cada campo

O teclado virtual é o teclado exibido na tela quando um campo de texto recebe o foco. O aplicativo pode pedir ao sistema um teclado adequado ao dado esperado. Isso importa porque, por exemplo, digitar um telefone em um teclado de letras obriga a trocar de modo a cada número, o que aumenta o tempo e a chance de erro. No Flutter, a escolha é feita pelo parâmetro keyboardType.

keyboardTypeTeclado que apareceUse em
TextInputType.textLetras (padrão)Nomes, descrições
TextInputType.numberSomente númerosSenhas numéricas, quantidades
TextInputType.phoneTeclado de discagemTelefone
TextInputType.emailAddressLetras, com @ e ponto em destaqueE-mail
TextInputType.multilineLetras, com tecla de nova linhaObservações longas
TextInputType.datetimeNúmeros com / e :Datas digitadas (prefira um seletor de data)

O parâmetro textInputAction define a tecla de ação do teclado: next leva ao próximo campo, done fecha o teclado e search exibe uma lupa. Assim, o usuário preenche o formulário inteiro sem precisar tocar em cada campo.

12.2 Formulário com validação

Validar um formulário é conferir se os dados atendem às regras do aplicativo antes de aceitá-los, por exemplo, se um campo obrigatório foi preenchido. A validação impede que dados incompletos entrem no sistema e, quando bem feita, orienta o usuário sobre como corrigir o problema.

No Flutter, um formulário validável tem quatro peças. O Form agrupa os campos. Cada TextFormField aceita uma função de validação. A GlobalKey<FormState> (chave global) permite que o código acesse o formulário para validar todos os campos de uma vez. O TextEditingController (controlador de edição de texto) guarda o texto digitado em um campo.

formulário de cadastro de item
class CadastroItemView extends StatefulWidget {
  const CadastroItemView({super.key});

  @override
  State<CadastroItemView> createState() => _CadastroItemViewState();
}

class _CadastroItemViewState extends State<CadastroItemView> {
  final _formKey = GlobalKey<FormState>();
  final _nome = TextEditingController();

  @override
  void dispose() {
    _nome.dispose(); // libera a memória do campo ao sair da tela
    super.dispose();
  }

  void _salvar() {
    if (!_formKey.currentState!.validate()) return; // mostra os erros
    ScaffoldMessenger.of(context).showSnackBar(
      SnackBar(content: Text('"${_nome.text}" cadastrado!')),
    );
    Navigator.of(context).pop();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Cadastrar item')),
      body: SingleChildScrollView( // rola quando o teclado abre
        padding: const EdgeInsets.all(16),
        child: Form(
          key: _formKey,
          child: Column(
            crossAxisAlignment: CrossAxisAlignment.stretch,
            children: [
              TextFormField(
                controller: _nome,
                textCapitalization: TextCapitalization.sentences,
                textInputAction: TextInputAction.next,
                decoration: const InputDecoration(
                  labelText: 'Nome do item',
                  hintText: 'Ex.: Furadeira de impacto',
                  border: OutlineInputBorder(),
                ),
                validator: (valor) {
                  if (valor == null || valor.trim().isEmpty) {
                    return 'Diga o nome do item.';
                  }
                  if (valor.trim().length < 3) {
                    return 'O nome precisa de pelo menos 3 letras.';
                  }
                  return null; // null = campo válido
                },
              ),
              const SizedBox(height: 16),
              TextFormField(
                keyboardType: TextInputType.multiline,
                maxLines: 3,
                decoration: const InputDecoration(
                  labelText: 'Observações (opcional)',
                  border: OutlineInputBorder(),
                ),
              ),
              const SizedBox(height: 24),
              FilledButton(onPressed: _salvar, child: const Text('Salvar')),
            ],
          ),
        ),
      ),
    );
  }
}

Entendendo o código

  1. _formKey é ligada ao formulário por key: _formKey. Por meio dela, _formKey.currentState dá acesso ao objeto que sabe validar todos os campos.
  2. _nome é o TextEditingController do campo "Nome do item", ligado por controller: _nome. O texto digitado fica em _nome.text.
  3. O método dispose() é chamado quando a tela é removida. Nele, _nome.dispose() libera os recursos do controlador; sem isso, ele continuaria ocupando memória depois de a tela ser fechada.
  4. Em _salvar(), validate() executa o validator de todos os campos. Se algum for inválido, devolve false, os erros aparecem abaixo dos campos e o return interrompe o salvamento. O ! em currentState! afirma ao Dart que o estado existe naquele momento.
  5. Se tudo for válido, showSnackBar exibe uma confirmação e pop() fecha o formulário.
  6. O validator recebe o texto em valor e segue uma regra: retorna a mensagem de erro se houver problema ou retorna null se o campo estiver correto. O trim() remove espaços nas pontas, para que um nome feito só de espaços seja recusado.
  7. labelText é o rótulo que permanece visível; hintText é o exemplo exibido enquanto o campo está vazio. O conteúdo fica dentro de um SingleChildScrollView para poder rolar quando o teclado abrir (seção 12.4).
E o MVC?

No exemplo, as regras ficaram dentro do validator apenas para o código caber em um bloco. Pelo MVC, regras de negócio não devem ficar na view. No aplicativo da squad, siga o projeto-base: as regras ficam em um controller (sessao_controller.dart), em métodos que devolvem a mensagem de erro ou null, e o campo apenas aponta para eles: validator: sessao.validarApartamento. Assim, as regras podem ser testadas separadamente e reaproveitadas em outras telas.

confirmação antes de agir (projeto-base, item_detalhe_view.dart)
final confirmou = await showDialog<bool>(
  context: context,
  builder: (context) => AlertDialog(
    title: const Text('Confirmar pedido?'),
    content: Text('Vamos avisar ${item.dono} que você quer pegar "${item.nome}".'),
    actions: [
      TextButton(
        onPressed: () => Navigator.pop(context, false),
        child: const Text('Cancelar'),
      ),
      FilledButton(
        onPressed: () => Navigator.pop(context, true),
        child: const Text('Confirmar'),
      ),
    ],
  ),
);
if (confirmou != true || !context.mounted) return;

Entendendo o código

  1. showDialog<bool> abre um diálogo e devolve um Future: a resposta só existe quando o usuário toca em um botão. Por isso a chamada usa await.
  2. O AlertDialog tem título, texto explicativo e botões em actions. O texto usa ${item.dono} e ${item.nome} para dizer exatamente o que vai acontecer.
  3. O diálogo é fechado com Navigator.pop, cujo segundo argumento é a resposta: false em "Cancelar" e true em "Confirmar".
  4. Se o usuário fechar o diálogo tocando fora dele, confirmou recebe null. Por isso o teste é confirmou != true: só uma confirmação explícita deixa a ação continuar.
  5. context.mounted verifica se a tela ainda faz parte da árvore de widgets. Durante o await, o usuário pode ter fechado a tela, e usar o context de uma tela que não existe mais causa erro. Regra: depois de todo await, confira context.mounted antes de usar o context.

12.4 Quando o teclado cobre o campo

O teclado virtual ocupa uma parte grande da tela. O Scaffold reduz automaticamente a altura do corpo quando ele abre, mas, se o conteúdo não couber e não puder rolar, surge a faixa de overflow (transbordamento) ou o campo fica escondido atrás do teclado. A regra é: toda tela com campo de texto deve ter o conteúdo dentro de um SingleChildScrollView ou de um ListView. Teste sempre no emulador de tela pequena, com o teclado aberto no último campo; esse cuidado é essencial para o Sr. Joaquim e seu celular antigo.

13.1 Hierarquia tipográfica

Hierarquia tipográfica é a organização dos textos de uma tela em níveis de importância, por meio do tamanho, do peso e do estilo da fonte. Ela permite perceber rapidamente o que é título, informação principal e detalhe; sem ela, todos os textos competem pela atenção.

O Material 3, sistema de design usado pelo Flutter, define papéis para o texto, disponíveis no TextTheme (tema de texto). Em vez de escolher um tamanho em cada tela, você escolhe o papel. Assim, o aplicativo fica consistente e uma mudança no tema se reflete em todas as telas.

13.2 Microtextos

Microtextos (microcopy) são os textos curtos da interface: rótulos de botões e campos, mensagens de erro e de confirmação, dicas. Embora curtos, são eles que orientam o usuário em cada passo. Siga estas regras para redigi-los.

  • O botão diz o que acontece: "Pedir emprestado" informa o resultado antes do toque; "OK" ou "Enviar" obrigam o usuário a deduzi-lo.
  • Use as palavras do usuário: "apartamento", e não "unidade habitacional". Termos burocráticos tornam a leitura mais lenta.
  • Mensagem de erro = o que aconteceu + como resolver, sem culpar a pessoa, para que ela consiga corrigir sozinha.
  • Seja breve: a interface é lida de passagem. Se a ideia cabe em três palavras, não use dez.
  • Mantenha o tom de voz: na UC1, o tom do Empresta Aí foi definido como "confiável, simples, vizinhança, sem frescura". Todos os textos devem segui-lo, para que o produto tenha uma só voz.

  • "Nenhum registro encontrado"

Texto que ajuda

13.3 Do guia de estilo ao código: o tema

O guia de estilo registra as decisões visuais do produto: cores, fontes, espaçamentos e formato dos componentes. Ele garante que toda a equipe tome as mesmas decisões. No Flutter, o guia se transforma em um ThemeData (dados de tema), definido em um único lugar e aplicado a todos os widgets.

Parte central do tema é o ColorScheme (esquema de cores), que reúne cores com funções definidas, como primary (principal), error (erro) e surface (fundo de superfícies). Como criar todas essas cores à mão, com bom contraste entre elas, é trabalhoso, o construtor ColorScheme.fromSeed gera o esquema completo a partir de uma única cor-semente, com tons harmoniosos para o modo claro e para o escuro.

lib/tema/tema.dart (projeto-base, resumido)
import 'package:flutter/material.dart';

class TemaEmprestaAi {
  static const Color corSemente = Color(0xFF00447C); // azul da agência

  // Espaçamentos padronizados: use sempre estes valores
  static const double espacoP = 8;
  static const double espacoM = 16;
  static const double espacoG = 24;

  static ThemeData claro() => _base(Brightness.light);
  static ThemeData escuro() => _base(Brightness.dark);

  static ThemeData _base(Brightness brilho) {
    return ThemeData(
      // Gera uma paleta completa e harmoniosa a partir de uma cor
      colorScheme: ColorScheme.fromSeed(seedColor: corSemente, brightness: brilho),
      filledButtonTheme: FilledButtonThemeData(
        style: FilledButton.styleFrom(
          minimumSize: const Size.fromHeight(52),
          textStyle: const TextStyle(fontSize: 17, fontWeight: FontWeight.w600),
        ),
      ),
      inputDecorationTheme: const InputDecorationTheme(border: OutlineInputBorder()),
    );
  }
}

// Em app.dart:
// MaterialApp(
//   theme: TemaEmprestaAi.claro(),
//   darkTheme: TemaEmprestaAi.escuro(), // modo escuro automático
//   ...
// )

Entendendo o código

  1. Os membros da classe são static: pertencem à classe e são usados sem criar objeto, como em TemaEmprestaAi.espacoM.
  2. corSemente está em hexadecimal: FF indica opacidade total e 00447C é o azul.
  3. espacoP, espacoM e espacoG padronizam os espaçamentos e evitam números soltos nas telas.
  4. claro() e escuro() chamam o mesmo _base, mudando só o Brightness; os dois modos compartilham as regras.
  5. ColorScheme.fromSeed gera o esquema de cores a partir da semente e do brilho. filledButtonTheme dá a todos os FilledButton altura mínima de 52 e texto 17 em seminegrito, e inputDecorationTheme dá borda contornada a todos os campos.
  6. Em app.dart, theme recebe o tema claro e darkTheme o escuro; o Flutter escolhe conforme a configuração do celular.
Conceito-chave

Depois que o tema existe, nenhuma tela deve ter cor escrita diretamente, como Colors.blue ou Color(0xFF...). Use sempre as cores do esquema: Theme.of(context).colorScheme.primary, .error, .surface e assim por diante. Uma cor escrita diretamente não muda no modo escuro e, se a marca mudar, precisará ser procurada em vários arquivos; com o tema, a mudança é feita em um só lugar.

Fontes personalizadas

Para usar uma fonte do Google Fonts, baixe os arquivos .ttf, coloque-os em assets/fontes/ e declare-os na seção fonts: do pubspec.yaml, ou use o pacote google_fonts. Em ambos os casos, registre a licença na planilha da Aula 8, como foi feito com as imagens, pois fontes também têm direitos de uso.

14.1 O que é um teste de usabilidade

Usabilidade é o quanto um produto permite que determinadas pessoas realizem suas tarefas com eficácia, eficiência e satisfação. O teste de usabilidade avalia essa qualidade observando o uso real, em vez de depender da opinião da equipe.

Conceito-chave

Em um teste de usabilidade, uma pessoa real tenta cumprir tarefas reais no aplicativo enquanto a squad observa, sem ajudar. Avalia-se se ela concluiu a tarefa (eficácia), quanto tempo levou e quantos erros cometeu (eficiência) e o que achou da experiência (satisfação). O que se testa é a interface, nunca a pessoa.

A regra de não ajudar existe porque, no uso real, o morador estará sozinho com o aplicativo. Uma dica da equipe esconde o problema da interface, que então não será corrigido. Cada dificuldade observada é uma informação para melhorar o produto.

No mercado

Pesquisas do Nielsen Norman Group, referência em usabilidade, indicam que testar com cerca de cinco usuários já revela a maior parte dos problemas de uma interface. Por isso, recomenda-se testar com poucas pessoas, corrigir e testar de novo, em vários ciclos, em vez de fazer um único teste grande no final.

14.2 Montando o roteiro

O roteiro de teste define, antes da sessão, o que será pedido ao participante e como o resultado será avaliado. Com ele, todos os participantes passam pelas mesmas tarefas e os resultados podem ser comparados.

  1. Tarefas realistas, escritas como situação, e não como instrução: "Sua pia entupiu e você precisa de um desentupidor. Veja se algum vizinho tem", e não "Toque na lupa e digite desentupidor". A instrução entrega o caminho e impede de saber se o usuário o encontraria sozinho.
  2. Três a cinco tarefas, cobrindo o fluxo principal; mais do que isso cansa o participante.
  3. Critério de sucesso de cada tarefa definido antes, por exemplo: "chegou à tela de detalhe e tocou em Pedir". Sem ele, a equipe tende a contar "quase conseguiu" como sucesso.
  4. Papéis: o facilitador conversa com o participante; o observador anota; o cronometrista mede o tempo.
  5. Pensar em voz alta: peça ao participante que diga o que está pensando enquanto usa ("estou procurando onde..."). Isso revela o raciocínio por trás de cada decisão.

14.3 Conduzindo com cordialidade

O participante costuma se sentir avaliado e pode ficar nervoso ao errar. Comentários, gestos ou dicas de quem conduz mudam seu comportamento e escondem os problemas reais.

Atrapalha o teste

  • "É fácil, é só tocar ali embaixo."
  • "Não, não é aí!"
  • Rir ou suspirar quando a pessoa erra.
  • Explicar o aplicativo antes de começar.

Teste bem conduzido

  • "Estamos testando o aplicativo, não você. Se algo for difícil, a responsabilidade é nossa."
  • "O que você esperava que acontecesse?"
  • Silêncio paciente quando a pessoa para em um ponto.
  • Agradecer sinceramente ao final.

A pergunta "O que você esperava que acontecesse?" não indica o caminho; apenas convida a pessoa a explicar sua expectativa, o que ajuda a entender a origem da dificuldade.

14.4 Registrando os resultados

Para cada participante e cada tarefa, anote na ficha: se concluiu (sim, com dificuldade ou não), o tempo, os erros, onde hesitou e frases marcantes. Esses registros permitem identificar os problemas que se repetem. Identifique os participantes apenas como Usuário A, B, C, sem nome, telefone ou foto, para proteger a privacidade de quem colaborou (veja a seção 15.5).

15.1 Os quatro pontos que mais reprovam um aplicativo

As recomendações de acessibilidade mais usadas no mundo são as WCAG (Web Content Accessibility Guidelines, Diretrizes de Acessibilidade para Conteúdo Web), publicadas pelo W3C. Criadas para a web, também são aplicadas a aplicativos. A versão atual é a 2.2, e o nível AA é o mais exigido. Junto com as orientações do Android e do Material Design, elas destacam quatro pontos.

Dois termos aparecem nesses critérios. A razão de contraste compara a luminosidade do texto com a do fundo, de 1:1 (nenhuma diferença) a 21:1 (preto sobre branco). O dp (density-independent pixel, pixel independente de densidade) é a unidade do Android e do Flutter que mantém aproximadamente o mesmo tamanho físico em telas de resoluções diferentes; 48 dp equivalem a cerca de 9 mm.

1. Contraste

Texto comum precisa de contraste de pelo menos 4,5:1 com o fundo; texto grande (a partir de 24 px, ou cerca de 19 px em negrito) e ícones, 3:1 (WCAG 2.2, nível AA, do W3C). O texto grande tolera menos contraste porque seus traços são mais fáceis de distinguir. Cinza-claro sobre branco quase sempre reprova e prejudica quem tem baixa visão ou usa o celular ao sol.

2. Alvo de toque

Mínimo de 48 × 48 dp em tudo que é tocável, conforme a recomendação do Android e do Material Design, com espaço entre alvos vizinhos. Alvos pequenos ou próximos demais causam toques errados, sobretudo para quem usa o polegar ou tem tremor nas mãos.

3. Rótulos para leitor de tela

O leitor de tela lê em voz alta o conteúdo da tela para pessoas cegas ou com baixa visão, e por isso cada elemento precisa de um rótulo em texto. Botão só com ícone precisa de tooltip; imagem com significado precisa de semanticLabel; imagem decorativa deve ser ignorada.

4. Texto ampliado

O aplicativo precisa continuar utilizável com a fonte do sistema no máximo, sem texto cortado nem sobreposto.

15.2 Acessibilidade no código Flutter

O leitor de tela não "enxerga" a imagem da tela. Ele lê a árvore de semântica, uma estrutura que o Flutter monta em paralelo à árvore de widgets e que descreve cada elemento em texto: o que é, qual é o rótulo e em que estado está. Muitos widgets do Material a preenchem sozinhos; um FilledButton com o texto "Salvar" é anunciado como botão "Salvar". Nos casos abaixo, o desenvolvedor precisa completar essas informações.

rótulos e semântica
// Botão só com ícone: o tooltip vira o rótulo lido pelo leitor de tela
IconButton(
  tooltip: 'Mostrar senha',
  icon: const Icon(Icons.visibility),
  onPressed: alternarSenha,
);

// Imagem com significado
Image.asset('assets/imagens/escada.webp', semanticLabel: 'Escada de alumínio de 7 degraus');

// Imagem só decorativa: o leitor de tela pula
Image.asset('assets/imagens/fundo.webp', excludeFromSemantics: true);

// Juntar um cartão inteiro numa frase só (projeto-base, item_card.dart)
Semantics(
  button: true,
  label: '${item.nome}, de ${item.dono}, ${disponivel ? 'Disponível' : 'Emprestado'}',
  excludeSemantics: true, // ignora os textos soltos de dentro
  child: Card(/* ... */),
);

Entendendo o código

  1. O tooltip do IconButton é a dica exibida ao manter o dedo sobre o botão e também o rótulo lido pelo leitor de tela ("Mostrar senha").
  2. semanticLabel descreve em palavras o que a imagem comunica; evite descrições genéricas como "imagem".
  3. excludeFromSemantics: true retira da árvore de semântica uma imagem decorativa, para que o leitor não anuncie algo sem informação.
  4. O widget Semantics define manualmente a descrição de uma parte da tela. Sem ele, o leitor anunciaria nome, dono e situação do item separadamente.
  5. button: true informa que o cartão é tocável. Em label, a expressão disponivel ? 'Disponível' : 'Emprestado' escolhe o primeiro texto se disponivel for verdadeiro e o segundo se for falso.
  6. excludeSemantics: true faz o leitor ignorar os textos internos do Card, evitando que sejam lidos duas vezes.

Parte dessas verificações pode ser feita por um teste automatizado: um código que executa o aplicativo em ambiente de teste e confere condições sem intervenção manual. O Flutter traz diretrizes prontas de contraste, alvo de toque e rótulos. O projeto-base já tem este teste em test/widget_test.dart:

test/widget_test.dart — teste automático de acessibilidade
testWidgets('Tela de entrada segue as diretrizes de acessibilidade', (tester) async {
  final handle = tester.ensureSemantics();
  await tester.pumpWidget(const EmprestaAiApp());

  await expectLater(tester, meetsGuideline(androidTapTargetGuideline)); // 48 dp
  await expectLater(tester, meetsGuideline(labeledTapTargetGuideline)); // rótulos
  await expectLater(tester, meetsGuideline(textContrastGuideline));     // contraste

  handle.dispose();
});

Entendendo o código

  1. testWidgets declara um teste de widgets: recebe uma descrição e uma função async com o tester, objeto que controla o aplicativo durante o teste.
  2. tester.ensureSemantics() liga a árvore de semântica, necessária para verificar rótulos. O handle devolvido serve para desligá-la no final com handle.dispose().
  3. await tester.pumpWidget(const EmprestaAiApp()) constrói o aplicativo no ambiente de teste.
  4. expectLater(tester, meetsGuideline(...)) verifica se a tela atende a uma diretriz; se não atender, o teste falha e indica o elemento problemático.
  5. androidTapTargetGuideline confere os alvos de 48 × 48 dp; labeledTapTargetGuideline, se todo elemento tocável tem rótulo; textContrastGuideline, o contraste dos textos segundo a WCAG.
terminal

Entendendo o código

  1. Executado na pasta do projeto, o comando roda todos os testes da pasta test/, incluindo os de acessibilidade e os de controllers_test.dart.
  2. Ao final, o terminal mostra quantos testes passaram. Se algum falhar, a mensagem indica o teste e o motivo; corrija a tela e execute de novo.
Atenção

O teste automatizado detecta apenas parte dos problemas. Ele verifica se um rótulo existe, mas não se faz sentido; também não avalia se a ordem de leitura é lógica nem se a tela é compreensível. Por isso, o teste com leitor de tela e com pessoas continua obrigatório.

15.3 Testando com o leitor de tela e com fonte grande

A verificação manual complementa o teste automatizado e coloca você no lugar de quem depende desses recursos. Os nomes dos menus podem variar entre fabricantes e versões do Android.

  1. TalkBack (Android): Configurações → Acessibilidade → TalkBack. Com ele ligado, um toque seleciona e lê o elemento; dois toques o ativam; deslizar para a direita passa ao próximo. No iPhone, o equivalente é o VoiceOver.
  2. Com os olhos fechados (ou a tela virada), tente cumprir a tarefa principal só ouvindo. Anote cada elemento lido de forma confusa ou não lido.
  3. Fonte grande: Configurações → Tela → Tamanho da fonte no máximo. Abra todas as telas e procure texto cortado, sobreposto ou com overflow.
  4. Visualizar a semântica: MaterialApp(showSemanticsDebugger: true, ...) mostra na tela o que o leitor de tela recebe. Remova a opção depois de conferir.

15.4 Emulador × dispositivo físico

O emulador não reproduz todas as condições reais: o toque com o dedo, o brilho e o reflexo da tela, o desempenho de um aparelho simples como o do Sr. Joaquim, a câmera e o leitor de tela real. Por isso, o aplicativo deve ser testado em pelo menos um celular físico. No Android:

  1. Em Configurações → Sobre o telefone, toque 7 vezes em Número da versão (em alguns aparelhos, "Número da compilação") para liberar as Opções do desenvolvedor.
  2. Em Opções do desenvolvedor, ative a Depuração USB, que permite ao computador instalar e controlar aplicativos no celular pelo cabo.
  3. Conecte o celular pelo cabo e aceite o aviso "Permitir depuração USB?". Autorize apenas computadores que você conhece.
  4. No terminal, flutter devices deve listar o aparelho. Depois, flutter run instala e abre o aplicativo nele.

15.5 Sigilo nos testes

Gravações da tela com a voz do participante, fotos e anotações são dados pessoais, isto é, informações que podem identificar alguém. A Lei Geral de Proteção de Dados Pessoais (LGPD, Lei nº 13.709/2018) exige que esses dados sejam tratados com base legal, como o consentimento, e usados apenas para a finalidade informada. Há também uma questão de confiança: quem colabora com um teste precisa ter certeza de que não será exposto.

Atenção

Peça autorização antes de gravar, identifique cada participante apenas como "Usuário A", "Usuário B" e assim por diante, nunca publique gravações no repositório nem em grupos de mensagens e apague as gravações depois que a avaliação for concluída. Essas regras valem também para os testes da Aula 14.

Para começar

16.1 Revisão de interface com feedback simulado

Um feedback de usuário é um relato de quem usa o produto sobre uma dificuldade, um erro ou uma sugestão. Para praticar o tratamento desse tipo de informação, cada squad recebe do docente, no início da aula, um feedback simulado: um relato preparado para a atividade, diferente para cada equipe, descrevendo uma tela confusa, um botão pequeno demais para o dedo, contraste insuficiente ou um texto ilegível.

Esse feedback entra na mesma lista que os achados das Aulas 14 e 15. Assim, problemas de fontes diferentes são comparados com os mesmos critérios.

16.2 Priorizando por gravidade e frequência

Priorizar é ordenar tarefas pela importância, para aplicar o esforço disponível onde ele gera mais benefício. Sem critério, a equipe tende a corrigir primeiro o que é mais fácil, deixando de lado problemas que impedem o uso. Por isso, usamos dois critérios objetivos.

A gravidade mede o quanto um problema atrapalha o usuário a concluir a tarefa. O pesquisador Jakob Nielsen propôs a escala de 0 a 4 abaixo, muito usada em avaliações de usabilidade.

NotaGravidade (escala de Nielsen)
0Não é problema de usabilidade.
1Cosmético: corrigir se sobrar tempo.
2Menor: atrapalha um pouco; baixa prioridade.
3Maior: atrapalha muito; alta prioridade.
4Catástrofe: impede a tarefa; corrigir antes de entregar.

A frequência indica quantos usuários tiveram o problema. Entre dois achados de nota 3, vem primeiro o que apareceu para todos os participantes. Quando o achado vem de um teste automático ou do checklist, registre a fonte no lugar da contagem. Há ainda uma regra que se sobrepõe às demais: problema de acessibilidade que impede alguém de usar o app é sempre nota 4, porque para essa pessoa ele é uma barreira completa.

Veja um exemplo de tabela de achados priorizada. A coluna "Decisão" mostra ao avaliador que a squad pensou sobre cada achado, inclusive os adiados.

#AchadoOndeGravidadeFrequênciaDecisão

Conceito-chave

Priorizar não é escolher o que é mais fácil. É ordenar os achados por gravidade e por frequência, lembrando que barreiras de acessibilidade são sempre nota 4. Toda decisão de adiar precisa de justificativa escrita.

16.3 Corrigindo com rastreabilidade

Rastreabilidade é a capacidade de seguir uma alteração desde a sua origem até a implementação, respondendo a perguntas como "qual teste motivou esta mudança?". Ela importa porque quem fizer a manutenção do app no futuro precisa entender as decisões sem depender da memória de quem as tomou. Você a obtém com três hábitos: uma branch por correção, uma mensagem de commit que cite o número do achado e, sempre que possível, capturas de tela de antes e depois.

terminal
git switch -c fix/rotulo-abas
# ... corrige ...
git commit -am "Adiciona rótulo de texto nas abas (achado 1 do teste)"
git push -u origin fix/rotulo-abas

Entendendo o código

  1. git switch -c fix/rotulo-abas cria a branch fix/rotulo-abas e passa a trabalhar nela. O prefixo fix/ indica, por convenção, uma correção.
  2. # ... corrige ... é um comentário: representa o momento em que você edita os arquivos para resolver o problema.
  3. git commit -am "..." registra as alterações. A opção -a inclui os arquivos já acompanhados pelo Git que foram modificados, e -m define a mensagem, que aqui cita o achado 1. Arquivos novos não entram com -a; para eles, use git add antes.
  4. git push -u origin fix/rotulo-abas envia a branch ao GitHub; -u associa a branch local à remota, para que os próximos envios dispensem o nome. Depois, a correção segue para revisão em um Pull Request.
Mão na massa

Passos: (1) montem a tabela de achados com os testes, o checklist e o feedback simulado; (2) atribuam gravidade e frequência a cada achado; (3) decidam o que corrigir agora e o que adiar, justificando; (4) corrijam pelo menos todos os achados nota 3 e 4, cada um em sua branch e com commit que cite o achado; (5) capturem telas de antes e depois. 19.1 Gerando o APK

Um APK (Android Package, pacote Android) é o arquivo de instalação de um aplicativo Android. Ele reúne o código compilado, as imagens e as demais informações necessárias à instalação. Com ele, o cliente instala o app no próprio celular, sem loja e sem cabo.

terminal
flutter build apk --release
# o arquivo fica em: build\app\outputs\flutter-apk\app-release.apk

Entendendo o código

  1. flutter build apk compila o projeto e gera o APK. Execute-o na pasta raiz do projeto, onde está o pubspec.yaml.
  2. --release gera a versão otimizada, sem ferramentas de depuração.
  3. O comentário iniciado por # indica onde o arquivo é salvo: build\app\outputs\flutter-apk\app-release.apk. É esse arquivo que vai para o celular.

Envie o arquivo para um celular Android e abra-o. Como o app não vem da loja, o Android pede permissão para instalar de fontes desconhecidas; conceda-a apenas a arquivos confiáveis, como o gerado pela sua squad.

Todo APK precisa ser assinado, isto é, receber uma assinatura digital feita com uma chave que identifica o autor. A assinatura garante que o app não foi alterado e que as atualizações vêm do mesmo desenvolvedor; o Android não instala APK sem ela. Em um projeto Flutter recém-criado, a versão release é assinada com a chave de depuração, o que basta para celulares de teste. Para publicar na Google Play, é obrigatório usar uma chave própria e cumprir outras etapas, que veremos nas próximas UC.

Conceito-chave

O app executado com flutter run está em modo debug (depuração): permite hot reload e inspeção, mas é mais lento e mostra a faixa "DEBUG" no canto. O APK gerado com --release está em modo release: compilado antecipadamente para código nativo, otimizado e sem ferramentas de desenvolvimento. É a versão que o usuário recebe; por isso, demonstre sempre a release.

19.2 Roteiro de demonstração (10 minutos)

Um roteiro de demonstração define o que mostrar, em que ordem e em quanto tempo. Sem ele, o tempo se perde em detalhes. A maior parte do tempo vai para a tarefa principal contada como história: em vez de tela por tela, mostre Seu Antônio pedindo uma furadeira até receber a confirmação.

TempoO que mostrar

4 minO app funcionando: tarefa principal do início ao fim, contada como uma história de usuário real.
2 minO que os testes revelaram e o que mudou (antes e depois).
1 minAcessibilidade: fonte grande e leitor de tela em uma tela.

Plano B obrigatório

Um plano de contingência é a alternativa preparada para o caso de algo falhar. Tenham o APK instalado em pelo menos um celular, um vídeo curto gravado da tela com a tarefa principal e o emulador já aberto antes de começar. Se a internet, o projetor ou o emulador falharem, a demonstração continua com outro recurso.

19.3 Revisão por pares

A revisão por pares é a avaliação de um trabalho feita por colegas, e não pelo docente. Quem está de fora percebe o que a equipe já não nota. Para ser útil, quem avalia deve ser específico e respeitoso, apontando o que observou e sugerindo melhoria; quem recebe anota sem rebater e decide depois, em equipe, o que ajustar.

Mão na massa

Atividade 19 — Ensaio cronometrado. Objetivo: deixar app e apresentação prontos para a demonstração final. Passos: (1) gerem o APK e instalem-no em um celular, testando a tarefa principal; (2) gravem o vídeo do plano B; (3) ensaiem seguindo o roteiro, com tempo marcado e todos os integrantes falando, enquanto outra squad assiste e preenche a Ficha de revisão por pares (modelo fornecido pelo docente); (4) invertam os papéis; (5) corrijam o que foi apontado e registrem os ajustes no repositório. Entrega: APK funcionando, ficha recebida e commits dos ajustes.

Para fixar

  2. O que é um APK e onde o Flutter salva o arquivo de release?
  3. Para que serve a assinatura de um aplicativo Android?
  4. Que atitudes tornam uma revisão por pares útil?

Resumo da aula

  • Debug serve ao desenvolvimento; release é a versão otimizada que se demonstra e entrega.
  • O APK é gerado com flutter build apk --release e instalado sem loja.
  • Todo APK é assinado; publicar na Google Play exige chave própria.
  • A demonstração segue um roteiro de dez minutos e tem plano B.

20.4 Autoavaliação e recuperação

A autoavaliação é a reflexão do estudante sobre o próprio desempenho, comparando o que produziu com os indicadores. Ela ajuda a reconhecer pontos fortes e lacunas. A avaliação por pares a complementa com a percepção dos colegas de squad.

Um indicador avaliado como PA ou NA não encerra a sua trajetória na unidade. A recuperação funciona como uma reentrega: você combina com o docente o que refazer ou completar e em qual prazo, guiado pela devolutiva.

Erros fazem parte do desenvolvimento de qualquer aplicativo. O Flutter costuma informar o problema no terminal ou na própria tela, por meio de uma mensagem em inglês. Ao encontrar um erro, leia a mensagem com atenção, procure-a nesta tabela e, se não encontrar, registre a mensagem completa para mostrar ao docente.

Mensagem ou sintomaCausa provável e solução
Faixa amarela e preta com A RenderFlex overflowed by N pixelsOs filhos de uma Row/Column não cabem. Envolva o filho que pode encolher em Expanded, ou a tela em SingleChildScrollView.
Vertical viewport was given unbounded heightListView direto dentro de Column. Envolva a lista em Expanded.
A tela não atualiza quando muda um valorFaltou setState (estado local) ou notifyListeners() no controller, ou a tela não está dentro de um ListenableBuilder.
Mudei e o hot reload não mostrouMudanças no main(), no initState ou no pubspec.yaml exigem hot restart (R) ou parar e rodar de novo.
Unable to load assetCaminho errado, ou imagem não declarada no pubspec.yaml, ou indentação errada nele. Confira e rode de novo.
Null check operator used on a null valueUm ! foi usado em algo que era nulo. Troque por ?? com valor padrão ou verifique antes.
No connected devicesEmulador fechado ou celular sem depuração USB. Rode flutter devices e abra o emulador.
Build do Android falha com erro de GradleProjeto dentro do OneDrive ou em caminho com espaço/acento. Mova para C:\projetos\. Depois, flutter clean e flutter run.
