ReferênciaA UC3 em uma página

A competência desta unidade é desenvolver interface gráfica para dispositivos móveis. Interface gráfica é tudo o que o usuário vê e toca: telas, botões, textos, imagens, a navegação entre telas e as respostas do aplicativo a cada toque. Salvar dados num servidor, usar câmera ou GPS fica para as UC4 e UC5. Aqui o objetivo é que o aplicativo pareça certo, funcione bem na mão e possa ser usado por qualquer pessoa, inclusive quem enxerga pouco ou tem dificuldade com o celular.

A ferramenta escolhida para a turma é o Flutter, framework do Google que gera aplicativos Android, iOS e web a partir de um único código escrito na linguagem Dart. Você vai sair da UC sabendo montar telas, ligar uma tela na outra, tratar toques e formulários, aplicar um tema visual e testar o resultado com pessoas reais.

Aula 1 · MobilizaçãoSistemas mobile e leitura dos requisitos

Antes de abrir o editor, a pergunta do dia: o que muda quando uma tarefa sai do computador e vai para uma tela de seis polegadas usada com o dedo?

1.1 O que é diferente no celular

Um aplicativo não é um site encolhido. O celular tem limitações e possibilidades próprias, e boa parte das decisões de interface desta UC sai desta tabela.

CaracterísticaNo computadorNo celularO que isso muda na interface
TelaGrande, horizontal, várias janelasPequena, vertical, uma tela por vezUma tarefa principal por tela; hierarquia visual clara; nada de tabelas largas
EntradaMouse preciso e teclado físicoDedo (impreciso) e teclado virtual que cobre metade da telaAlvos de toque grandes; poucos campos de digitação; teclado certo para cada campo
Contexto de usoSentado, com atençãoEm pé, andando, com uma mão, com sol na tela, sendo interrompidoContraste alto; ações principais ao alcance do polegar; textos curtos
ConectividadeEstávelOscila entre Wi-Fi, 4G/5G e sem sinalMostrar carregamento e erro de rede com mensagem útil
Bateria e memóriaPraticamente ilimitadasLimitadas, principalmente em aparelhos antigosImagens leves; animações moderadas; nada pesado à toa
SensoresPoucosCâmera, GPS, acelerômetro, biometria, vibraçãoNovas formas de interação (vibrar ao confirmar, digital para entrar) — usadas nas UC4 e UC5

1.2 Plataformas e abordagens

Dois sistemas operacionais dominam o mercado: Android (Google, maioria dos aparelhos no Brasil) e iOS (Apple, iPhone). Há três jeitos principais de construir um aplicativo para eles:

AbordagemComo funcionaExemplos de tecnologia
NativoUm código para cada sistema, na linguagem oficial dele. Máximo desempenho, custo dobrado.Kotlin (Android), Swift (iOS)
HíbridoUma página web (HTML, CSS, JavaScript) roda dentro de um aplicativo. Aproveita quem já sabe web.Ionic, Capacitor, Cordova; PWA
Multiplataforma (cross-platform)Um único código gera aplicativos para vários sistemas, com desempenho próximo do nativo.Flutter (Dart), React Native (JavaScript), Kotlin Multiplatform
Conceito-chave

Flutter é um kit de desenvolvimento de interfaces criado pelo Google. Com um único código em Dart, ele gera aplicativos para Android, iOS, web e desktop. Diferente do híbrido, o Flutter não usa uma página web por dentro: ele desenha cada pixel da tela com seu próprio motor gráfico. Por isso a interface fica igual em todos os aparelhos.

No mercado

Flutter é usado em aplicativos de bancos, varejo e mobilidade no Brasil e no mundo, e é uma das tecnologias multiplataforma mais procuradas em vagas para desenvolvedor mobile. Para uma agência pequena como a nossa, a vantagem é direta: uma squad, um código, dois sistemas.

1.3 Lendo requisitos e wireframes como desenvolvedor

Na UC1 vocês escreveram requisitos para o cliente entender. Agora vão ler os mesmos documentos com outra pergunta: o que eu preciso construir? Para cada wireframe, procure:

  • Telas: quantas são e qual o nome de cada uma.
  • Fluxos: de qual tela se chega em qual, e por qual botão ou gesto.
  • Elementos: listas, formulários, imagens, botões, abas.
  • Estados: como a tela fica vazia, carregando, com erro, com sucesso. Wireframes quase nunca mostram isso, e o desenvolvedor precisa perguntar.
  • Dúvidas: o que o wireframe não responde. Exemplo: "o que aparece se o morador buscar um item que ninguém tem?"

2.3 Criando o emulador

  1. No Android Studio, abra Device Manager e clique em + (Create Virtual Device).
  2. Escolha um modelo de celular (por exemplo, um Pixel de tela média) e uma imagem de sistema recente.
  3. Crie um segundo emulador com tela pequena e sistema mais antigo. Ele representa o celular do Sr. Joaquim.
  4. Inicie um dos emuladores e, no terminal, confira se o Flutter o enxerga com flutter devices.
Conceito-chave

Os parâmetros de hardware de um emulador (tamanho e densidade da tela, memória, versão do Android) mudam como o aplicativo aparece e se comporta. Testar só no emulador "bonito" esconde problemas que o usuário real vai encontrar. Por isso trabalhamos sempre com pelo menos dois perfis.

Emulador não abre?

O emulador precisa da virtualização ativada no computador (Intel VT-x ou AMD-V, na BIOS) e, no Windows, do recurso Plataforma do Hipervisor do Windows. Se a máquina não suportar, rode o app no Chrome (flutter run -d chrome) ou no seu celular por cabo USB (passo a passo na Aula 15).

Aula 3 · MobilizaçãoVersionamento: ramificações e tags

Quatro pessoas mexendo no mesmo aplicativo ao mesmo tempo. Sem um combinado de versionamento, alguém apaga o trabalho de alguém até sexta-feira.

3.1 Ramificações (branches)

Conceito-chave

Uma ramificação (branch) é uma linha paralela de trabalho. A main guarda a versão que funciona; cada tela ou correção nasce em uma branch própria e só volta para a main depois de revisada. Uma tag é uma etiqueta fixa num ponto da história, como v0.1.0, usada para marcar entregas.

3.2 Combinados da squad

ItemCombinado sugerido
Nome das branchesfeature/tela-entrada, feature/lista-itens, fix/contraste-botao
Mensagem de commitVerbo no presente + o que mudou: Adiciona validação no campo de apartamento. Nada de "ajustes" ou "agora vai".
Integração na mainSempre por Pull Request, com revisão de pelo menos um colega.
Tagsv0.1.0 no Checkpoint 1, v0.2.0 no Checkpoint 2, v1.0.0 na demonstração final.

Aula 4 · DesenvolvimentoLeiaute para aplicativo móvel

Leiaute é a decisão de onde cada coisa fica na tela e por quê. Hoje vemos os princípios e como o Flutter os transforma em código.

4.1 Princípios de comunicação visual

Hierarquia

O que é mais importante aparece primeiro e maior. Em cada tela, deve ficar óbvio qual é a ação principal.

Contraste

Diferença clara entre texto e fundo, e entre o botão principal e os secundários.

Alinhamento

Elementos alinhados a uma mesma margem parecem organizados. Use sempre os mesmos espaçamentos (8, 16, 24).

Proximidade

O que é relacionado fica junto; o que é diferente fica separado. Rótulo colado no campo, grupos separados por espaço.

4.2 A zona do polegar e o tamanho do toque

A maioria das pessoas segura o celular com uma mão e alcança a tela com o polegar. A parte de baixo e o centro são fáceis de alcançar; os cantos de cima, difíceis.

Conceito-chave

Todo elemento tocável precisa de uma área de pelo menos 48 × 48 dp (diretriz do Material Design, do Google) ou 44 × 44 pt (diretriz da Apple). dp (pixel independente de densidade) é a unidade que o Flutter usa: 48 dp têm mais ou menos o mesmo tamanho físico em qualquer celular, cerca de 9 mm, a largura da ponta de um dedo.

4.3 Cores e entrada de dados

  • Regra 60-30-10: 60% da tela numa cor neutra (fundo), 30% numa cor secundária (superfícies, cartões) e 10% na cor de destaque (botões e ações). Destaque em tudo não destaca nada.
  • Cor não pode ser a única informação: "Disponível" em verde e "Emprestado" em vermelho precisam do texto escrito, porque cerca de 8% dos homens têm algum tipo de daltonismo.
  • Escolha o método de entrada mais fácil: antes de pedir para digitar, veja se dá para escolher numa lista, marcar um botão de opção ou usar um seletor de data. Digitar no celular é lento e cansativo.

Aula 6 · DesenvolvimentoArquitetura em camadas e MVC

Um aplicativo onde tudo fica num arquivo só funciona por duas semanas. Depois ninguém mais acha nada. Hoje definimos onde cada coisa mora.

6.1 Model, View, Controller

Conceito-chave

MVC divide o aplicativo em três camadas com responsabilidades separadas. Model: os dados e suas regras (um item, um pedido). View: o que aparece na tela. Controller: recebe as ações do usuário, altera o model e avisa a view que algo mudou. A view nunca altera dados diretamente; ela pede ao controller.

6.2 Como fica no Flutter

O Flutter não obriga nenhuma arquitetura, então a squad combina. Nesta UC usamos uma versão simples do MVC, com pastas assim:

estrutura de pastas
lib/
├── main.dart          só chama runApp()
├── app.dart           MaterialApp, tema, primeira tela
├── models/            MODEL: classes de dados (item.dart)
├── controllers/       CONTROLLER: regras e estado (itens_controller.dart)
├── views/             VIEW: uma tela por arquivo (itens_view.dart)
├── widgets/           pedaços reutilizáveis de tela (item_card.dart)
└── tema/              cores, fontes e espaçamentos (tema.dart)

O model é uma classe Dart comum, sem nada de tela:

lib/models/item.dart
class Item {
  final String id;
  final String nome;
  final String dono;
  bool disponivel;

  Item({
    required this.id,
    required this.nome,
    required this.dono,
    this.disponivel = true,
  });
}

O controller herda de ChangeNotifier, uma classe do próprio Flutter que sabe avisar quem estiver ouvindo:

lib/controllers/itens_controller.dart (resumido)
import 'package:flutter/foundation.dart';
import '../models/item.dart';

class ItensController extends ChangeNotifier {
  final List<Item> _itens = [
    Item(id: '1', nome: 'Furadeira de impacto', dono: 'Seu Antônio'),
    Item(id: '2', nome: 'Escada de alumínio', dono: 'Dona Ilza'),
  ];

  List<Item> get itens => List.unmodifiable(_itens);

  bool pedir(Item item) {
    if (!item.disponivel) return false;
    item.disponivel = false;
    notifyListeners(); // avisa as telas: "algo mudou, redesenhem"
    return true;
  }
}

A view usa ListenableBuilder para se redesenhar sempre que o controller avisar:

lib/views/itens_view.dart (resumido)
class ItensView extends StatelessWidget {
  const ItensView({super.key, required this.controller});
  final ItensController controller;

  @override
  Widget build(BuildContext context) {
    return ListenableBuilder(
      listenable: controller,
      builder: (context, _) {
        return ListView(
          children: [
            for (final item in controller.itens)
              ListTile(
                title: Text(item.nome),
                subtitle: Text(item.disponivel ? 'Disponível' : 'Emprestado'),
                onTap: () => controller.pedir(item),
              ),
          ],
        );
      },
    );
  }
}

6.3 StatelessWidget e StatefulWidget

StatelessWidget

Não guarda nada que mude. Recebe dados e desenha. A maioria das telas e componentes é assim: ItemCard, PerfilView.

StatefulWidget

Guarda um estado local que muda com o uso (a aba selecionada, a senha visível ou não). Para mudar, chama setState(() { ... }), que redesenha o widget.

Atenção

Estado que só interessa a uma tela (aba atual, campo visível) pode ficar no StatefulWidget com setState. Estado que várias telas usam (lista de itens, meus pedidos) fica no controller. Misturar os dois é a origem de metade dos bugs de "a tela não atualiza".

No mercado

Em projetos maiores, as equipes usam pacotes de gerência de estado como Provider, Riverpod ou Bloc, e arquiteturas como MVVM. Todos partem da mesma ideia que vocês estão aplicando aqui: separar tela, regra e dados. Quem entende o ChangeNotifier aprende qualquer um deles depois.

7.2 Webstandards: as boas práticas do W3C

  • HTML semântico: usar a tag que diz o que a coisa é (<button>, <nav>, <h1>), não <div> para tudo. Leitores de tela dependem disso.
  • Separação de responsabilidades: estrutura no HTML, aparência no CSS, comportamento no JavaScript. É o mesmo raciocínio do MVC.
  • Viewport e unidades relativas: a meta tag viewport e medidas como %, rem e vw fazem a página se adaptar ao celular.
  • Validação: o código deve passar no validador do W3C (validator.w3.org) sem erros.

7.3 Progressive Web Apps (PWA)

Conceito-chave

Uma PWA é um site que se comporta como aplicativo: pode ser instalado na tela inicial, abre em tela cheia e pode funcionar sem internet. Ela depende de três coisas: HTTPS, um arquivo manifest (nome, ícones e cores do app) e um service worker (um script que guarda arquivos para uso offline).

manifest.json — o "cartão de identidade" de uma PWA
{
  "name": "Empresta Aí",
  "short_name": "Empresta Aí",
  "start_url": ".",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#00447c",
  "icons": [
    { "src": "icons/Icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "icons/Icon-512.png", "sizes": "512x512", "type": "image/png" }

O Flutter também gera versão web: o comando flutter build web cria a pasta build/web, já com um manifest.json e ícones parecidos com esses (veja web/manifest.json no seu projeto). A diferença é que a versão web do Flutter desenha a tela num canvas, não em HTML semântico. Por isso ela é ótima para aplicativos, e pior que um site comum para conteúdo que precisa aparecer no Google.

8.3 Como otimizar

  1. Redimensione para o tamanho máximo em que a imagem aparece (em pixels, já multiplicado pela densidade 3x). Uma foto de 4000 px para um espaço de 360 dp é desperdício.
  2. Converta para o formato certo (fotos em WebP ou JPG; ícones em SVG ou PNG).
  3. Comprima com uma ferramenta como Squoosh (squoosh.app, no navegador) ou TinyPNG.
  4. Meça o antes e o depois e anote o ganho. É evidência para o relatório.
  5. Prefira ícones a imagens quando possível: o Flutter já traz milhares de ícones Material (Icon(Icons.handyman)) que não pesam nada.

Aula 11 · DesenvolvimentoInteração I: toque e navegação

Até aqui, telas soltas. Hoje elas viram um aplicativo: cada toque leva a algum lugar, e o usuário sempre sabe onde está e como voltar.

11.1 Respondendo ao toque

Botões já têm onPressed. Para tornar tocável qualquer outra coisa (um cartão, uma imagem), use InkWell, que mostra o efeito de "onda" do Material, ou GestureDetector, que reconhece mais gestos mas não mostra efeito visual.

eventos de toque
// Botão: o jeito mais simples
FilledButton(
  onPressed: () => print('tocou'),
  child: const Text('Pedir'),
);

// Qualquer widget tocável, com efeito visual
Card(
  clipBehavior: Clip.antiAlias, // a "onda" respeita os cantos arredondados
  child: InkWell(
    onTap: () => abrirDetalhe(),
    onLongPress: () => mostrarOpcoes(),
    child: const ListTile(title: Text('Escada de alumínio')),
  ),
);

// Gestos mais avançados (arrastar, toque duplo), sem efeito visual
GestureDetector(
  onDoubleTap: () => favoritar(),
  child: const Icon(Icons.favorite_border),
);
Atenção

Gesto escondido (toque longo, toque duplo, deslizar) nunca pode ser o único jeito de fazer algo. Seu Antônio não vai descobrir sozinho que precisa segurar o dedo no item. Sempre ofereça também um botão visível.

11.2 Alternância entre telas com o Navigator

Conceito-chave

O Navigator funciona como uma pilha de pratos. push coloca uma tela nova em cima; pop tira a de cima e revela a anterior. O botão "voltar" do Android e a seta da AppBar fazem pop automaticamente.

abrir uma tela passando dados, e voltar
// Na lista: abrir o detalhe do item tocado
Navigator.of(context).push(
  MaterialPageRoute(
    builder: (context) => ItemDetalheView(item: item),
  ),
);

// No detalhe: voltar para a lista
Navigator.of(context).pop();

// Trocar a tela atual sem permitir voltar (ex.: depois do login)
Navigator.of(context).pushReplacement(
  MaterialPageRoute(builder: (context) => const InicioView()),
);

// Esperar uma resposta da tela que foi aberta
final confirmou = await Navigator.of(context).push<bool>(
  MaterialPageRoute(builder: (context) => const ConfirmarView()),
);
// e, na ConfirmarView: Navigator.of(context).pop(true);

11.4 Limitações e possibilidades de navegação

  • Profundidade: se o usuário precisa de mais de três toques para chegar ao que quer, repense o fluxo.
  • Voltar previsível: o botão voltar deve levar para onde o usuário espera. Depois do login, voltar não deve retornar à tela de senha (por isso o pushReplacement).
  • Sair sem perder dados: se o usuário preencheu um formulário e aperta voltar, pergunte antes de descartar. O widget PopScope permite interceptar o voltar.
  • Onde estou? Título na AppBar e aba destacada sempre mostram a posição atual.

class CadastroItemView extends StatefulWidget {
  const CadastroItemView({super.key});

  @override
  State<CadastroItemView> createState() => _CadastroItemViewState();
}

class _CadastroItemViewState extends State<CadastroItemView> {
  final _formKey = GlobalKey<FormState>();
  final _nome = TextEditingController();

  @override
  void dispose() {
    _nome.dispose(); // libera a memória do campo ao sair da tela
    super.dispose();
  }

  void _salvar() {
    if (!_formKey.currentState!.validate()) return; // mostra os erros
    ScaffoldMessenger.of(context).showSnackBar(
      SnackBar(content: Text('"${_nome.text}" cadastrado!')),
    );
    Navigator.of(context).pop();
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Cadastrar item')),
      body: SingleChildScrollView( // rola quando o teclado abre
        padding: const EdgeInsets.all(16),
        child: Form(
          key: _formKey,
          child: Column(
            crossAxisAlignment: CrossAxisAlignment.stretch,
            children: [
              TextFormField(
                controller: _nome,
                textCapitalization: TextCapitalization.sentences,
                textInputAction: TextInputAction.next,
                decoration: const InputDecoration(
                  labelText: 'Nome do item',
                  hintText: 'Ex.: Furadeira de impacto',
                  border: OutlineInputBorder(),
                ),
                validator: (valor) {
                  if (valor == null || valor.trim().isEmpty) {
                    return 'Diga o nome do item.';
                  }
                  if (valor.trim().length < 3) {
                    return 'O nome precisa de pelo menos 3 letras.';
                  }
                  return null; // null = campo válido
                },
              ),
              const SizedBox(height: 16),
              TextFormField(
                keyboardType: TextInputType.multiline,
                maxLines: 3,
                decoration: const InputDecoration(
                  labelText: 'Observações (opcional)',
                  border: OutlineInputBorder(),
                ),
              ),
              const SizedBox(height: 24),
              FilledButton(onPressed: _salvar, child: const Text('Salvar')),
            ],
          ),
        ),
      ),
    );
  }
}

13.2 Microtextos

Microtextos são os textos curtos da interface: botões, rótulos, mensagens, dicas. Algumas regras:

  • Botão diz o que acontece: "Pedir emprestado", não "OK" nem "Enviar".
  • Fale como o usuário fala: "apartamento", não "unidade habitacional".
  • Mensagem de erro = o que aconteceu + como resolver, sem culpar a pessoa.
  • Seja breve: se cabe em três palavras, não use dez.
  • Tom de voz consistente: o Empresta Aí é "confiável, simples, vizinhança, sem frescura" (definido na UC1). Isso vale para todos os textos.

Texto que atrapalha

  • "Submeter solicitação"
  • "Erro: campo obrigatório"
  • "Falha na operação. Código 500."
  • "Nenhum registro encontrado"

Texto que ajuda

  • "Pedir emprestado"
  • "Diga o nome do item."
  • "Não conseguimos enviar agora. Confira sua internet e tente de novo."
  • "Ninguém cadastrou esse item ainda. Que tal perguntar no grupo?"

Aula 14 · DesenvolvimentoTestes em mobile I: usabilidade

Vocês conhecem o app de cor, então não conseguem mais enxergar onde ele confunde. Precisamos de gente que nunca viu o aplicativo.

14.1 O que é um teste de usabilidade

Conceito-chave

Num teste de usabilidade, uma pessoa real tenta cumprir tarefas reais no aplicativo enquanto a squad observa, sem ajudar. Mede-se se ela conseguiu (eficácia), quanto tempo e quantos erros levou (eficiência) e o que achou (satisfação). O que se testa é a interface, nunca a pessoa.

No mercado

A pesquisa do Nielsen Norman Group, referência na área, mostra que testar com cerca de cinco usuários já revela a maior parte dos problemas de usabilidade de uma interface. Vale mais testar pouco e várias vezes do que uma vez só, com muita gente, no final.

14.2 Montando o roteiro

  1. Tarefas realistas, escritas como situação, não como instrução: "Sua pia entupiu e você precisa de um desentupidor. Veja se algum vizinho tem", e não "Toque na lupa e digite desentupidor".
  2. Três a cinco tarefas, cobrindo o fluxo principal do app.
  3. Critério de sucesso de cada tarefa definido antes ("chegou à tela de detalhe e tocou em Pedir").
  4. Papéis: um facilitador (conversa com o usuário), um observador (anota) e um cronometrista.
  5. Pensar em voz alta: peça para o usuário falar o que está pensando enquanto usa ("estou procurando onde...").

14.3 Conduzindo com cordialidade

Atrapalha o teste

  • "É fácil, é só tocar ali embaixo."
  • "Não, não é aí!"
  • Rir ou suspirar quando a pessoa erra.
  • Explicar o app antes de começar.

Teste bem conduzido

  • "Estamos testando o aplicativo, não você. Se algo for difícil, a culpa é nossa."
  • "O que você esperava que acontecesse?"
  • Silêncio paciente quando a pessoa trava.
  • Agradecer ao final, de verdade.

14.4 Registrando

Para cada usuário e cada tarefa, anote na ficha: conseguiu (sim / com dificuldade / não), tempo, erros, onde hesitou e frases marcantes. Identifique os participantes só como Usuário A, B, C: nada de nome, telefone ou foto.

Aula 15 · DesenvolvimentoTestes em mobile II: acessibilidade e dispositivo físico

Acessibilidade não é acabamento, é requisito. No Empresta Aí, se Seu Antônio não consegue usar, o produto falhou. Hoje testamos o app com os olhos, as mãos e os ouvidos de quem tem alguma limitação.

15.1 Os quatro pontos que mais reprovam um app

1. Contraste

Texto comum precisa de contraste de pelo menos 4,5:1 com o fundo; texto grande (a partir de 24 px, ou cerca de 19 px em negrito) e ícones, 3:1 (WCAG 2.2, nível AA, do W3C). Cinza-claro sobre branco quase sempre reprova.

2. Alvo de toque

Mínimo de 48 × 48 dp em tudo que é tocável, com espaço entre alvos vizinhos.

3. Rótulos para leitor de tela

Botão só com ícone precisa de tooltip; imagem com significado precisa de semanticLabel; imagem decorativa deve ser ignorada.

4. Texto ampliado

O app precisa continuar usável com a fonte do sistema no máximo, sem texto cortado nem sobreposto.

O teste automático pega só uma parte dos problemas. Ele não sabe se o rótulo faz sentido, se a ordem de leitura é lógica ou se a tela é compreensível. O teste com o leitor de tela e com pessoas continua obrigatório.

15.3 Testando com o leitor de tela e fonte grande

  1. TalkBack (Android): Configurações → Acessibilidade → TalkBack. Com ele ligado, um toque seleciona e lê; dois toques ativam; deslizar para a direita vai ao próximo elemento. No iPhone, o equivalente é o VoiceOver.
  2. Com os olhos fechados (ou a tela virada), tente cumprir a tarefa principal do app só ouvindo. Anote cada elemento lido de forma confusa ou não lido.
  3. Fonte grande: Configurações → Tela → Tamanho da fonte no máximo. Abra todas as telas e procure texto cortado, sobreposto ou com overflow.
  4. Visualizar a semântica: no código, MaterialApp(showSemanticsDebugger: true, ...) mostra na tela o que o leitor de tela "enxerga".

15.4 Emulador × dispositivo físico

O emulador não mostra tudo: o toque com o dedo de verdade, o brilho e reflexo da tela, o desempenho de um aparelho simples, a câmera e o leitor de tela real. Para rodar no seu celular Android:

  1. Em Configurações → Sobre o telefone, toque 7 vezes em Número da versão para liberar as Opções do desenvolvedor.
  2. Em Opções do desenvolvedor, ative Depuração USB.
  3. Ligue o celular no computador pelo cabo e aceite o aviso "Permitir depuração USB?" na tela do celular.
  4. No terminal, flutter devices deve listar o aparelho. Depois, flutter run.

19.1 Gerando o APK

Um APK é o arquivo de instalação de um aplicativo Android. Com ele, o cliente instala o app no próprio celular, sem loja e sem cabo.

terminal
flutter build apk --release
# o arquivo fica em: build\app\outputs\flutter-apk\app-release.apk

Envie o arquivo para um celular Android, abra e permita a instalação de fontes desconhecidas quando o sistema pedir. Para publicar na Google Play, o processo exige assinatura com chave própria e outras etapas, que veremos nas próximas UC.

Conceito-chave

O app rodando com flutter run está em modo debug: mais lento, com a faixa "DEBUG" no canto e ferramentas de desenvolvimento ligadas. O APK gerado com --release é a versão otimizada que o usuário recebe. Demonstre sempre a versão release, porque é ela que vale.
